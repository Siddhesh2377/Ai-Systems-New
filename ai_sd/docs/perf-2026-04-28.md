# ai_sd Performance Notes — 2026-04-28

Where time goes today, where the big wins still are, and what's worth trying
on each backend (CPU / NPU / GPU). All numbers are anchored to Snapdragon 7s
Gen 3 (HTP V73, 4× A78 + 4× A55, Adreno 710, LPDDR5 ≈ 17 GB/s).

## Current state

### What's already in
- **CPU affinity**: `pin_to_perf_cores()` on JNI entry pins the calling thread
  group to A78 cores via `sched_setaffinity` (`utils/cpu_affinity.h:56`).
  Without this, the scheduler mixes A78+A55 → measured 2-4× slowdown.
- **MNN CPU**: `numThread = 4`, `Power_High`, `Memory_Low` for CLIP/UNet/VAE.
- **MNN OpenCL**: enabled via `MNN_OPENCL=ON` in CMake. Used selectively for
  UNet/VAE encoder/VAE decoder/depth when `useOpenCL=true` is passed. Mode is
  `MNN_GPU_MEMORY_BUFFER | MNN_GPU_TUNING_FAST` with FP16 precision.
- **MNN BF16**: built but not currently activated at runtime.
- **MNN NNAPI**: built but disabled at runtime — Adreno NNAPI driver is buggy.
- **Persistent sessions**: UNet + VAE (encoder + decoder) sessions are cached
  across generations (Perf 7) — saves 200-500 ms per gen.
- **Pre-allocated buffers**: latents_in/out, noise_pred, etc. live in
  `PipelineContext::Buffers` (Perf 1) — eliminates ~256 KB heap churn per step.
- **CFG=1 fast path** *(new today)*: when `cfg_scale == 1.0`, the QNN path
  runs only the cond UNet pass (`unet_runner.cpp:142+`). ~2× speedup.
- **CLIP cache** *(new today)*: same `(prompt, neg, dim, v2)` skips inference.
  Cleared on model swap.

### What's measured (anchor: 7s Gen 3 @ 512×512)
- CLIP encode (MNN CPU): ~140 ms
- UNet step (QNN HTP V73): ~1.1 s — dominated by NPU compute, not host.
- UNet step (MNN CPU 4 threads): ~6 s — dominated by GEMM.
- VAE decode (MNN CPU): ~750 ms; (OpenCL): ~210 ms but watchdog risk.
- Per-image total at 20 steps QNN: ~24 s.

## CPU side — wins still on the table

1. **MNN BF16 weight inference** — already built (`MNN_SUPPORT_BF16=ON`) but
   not enabled at session creation. Set
   `bkCfg.precision = MNN::BackendConfig::Precision_BF16` for the CPU path
   on UNet/VAE; expect ~25-35% step-time reduction with negligible quality loss.
   Risk: needs verification on each model — some quantized weights will refuse.
2. **GEMV fast path on prefill** — already noted in `gguf_lib`'s heterogeneous
   plan. SD's CLIP encoder is one-shot, so this matters less; UNet doesn't
   degenerate to GEMV.
3. **NEON `int4`/`int8` GEMM** — MNN_LOW_MEMORY is on; KleidiAI is OFF
   (CMake 3.22 cross-compile failure noted in repo memory). Re-enabling
   KleidiAI would unlock A78's i8mm path → 1.4-1.8× on dot-product GEMM.
   Worth trying with a newer CMake.
4. **A78-only thread count** — current `numThread=4` is correct for 4 big
   cores, but if the device has only 2 perf cores (mid-range) it's hurting.
   Read `cpu_affinity.h`'s perf-core count and pass it to MNN.
5. **Avoid sequential CLIP runs** — CLIP runs negative then positive. They
   are independent. On CPU, batch them as a single forward pass with
   `batch=2` after rebuilding the session — saves ~50% of CLIP time. Low
   priority since CLIP is now cached.

## NPU / QNN HTP — wins still on the table

1. **CFG=1 skip** ✅ done today. Check that the LCM scheduler is paired with
   `cfg=1.0` from the API surface so this fires.
2. **QNN HTP context-binary cache reuse** — the QNN libs ship with HTP context
   binaries (`libQnnHtpV{N}.so`). On first generation, the model graph is
   compiled per-device and cached in `cacheDir`. Today this reuse only happens
   if `setCacheFile()` is called for MNN — the QNN side relies on
   `model_loader` and may be re-compiling on every cold start. Confirm by
   timing the first vs. second generation after a fresh install.
3. **HTP power profile** — QNN exposes
   `QnnHtpPerfInfrastructure_PowerConfigId_t` with profiles
   `BURST → SUSTAINED_HIGH_PERFORMANCE → POWER_SAVER`. We don't currently set
   one; default is heuristic. Set BURST during the UNet loop, drop back at
   end. Expect 5-15% throughput on long generations.
4. **Async dispatch + overlap** — `executeUnetGraphs(uncond)` and
   `executeUnetGraphs(cond)` are sequential. With QNN's async event API they
   could overlap with the CPU CFG combine of the previous step. Modest
   (~5-10%) but free once wired.
5. **W8A16 vs W8A8** — the xororz QNN bundles are W8A16 (weights int8,
   activations int16). Some 8 Gen 3 models offer W8A8 variants which are
   ~30% faster but lossier. Adding "min/8gen2/8gen3/8gen3-fast" variant
   selection in the SDK would let the host pick.

## GPU (Adreno OpenCL) — practical reality

The user is right about the watchdog: **Android-Adreno UMA imposes a 2 s
display-thread watchdog** (Khronos `CL_KERNEL_TIMED_OUT_QCOM` is rare; more
commonly the kernel just gets killed and OpenCL returns -38). For SD work
the watchdog manifests as VAE decode killing the GUI thread on large
resolutions.

What this means in practice:
- **VAE decode on OpenCL**: 750 ms → 210 ms is real, but at 768×768 it
  pushes the 2 s envelope at high system load. Tile the decode (already
  done via `vae_codec.cpp` Laplacian blending) — keep tiles ≤ 256² to stay
  well under watchdog.
- **UNet on OpenCL**: a single forward at 512×512 takes ~700 ms on Adreno
  710. Marginally faster than CPU, much slower than HTP, and uses the same
  power budget as the display server. Not worth it on this SoC.
- **UNet on Adreno 740/750 (8 Gen 2/3)**: closer to 250 ms — competitive
  with HTP for short generations, **but** thermal-throttles after 3-4
  consecutive runs. HTP wins on sustained throughput.

Recommendations:
1. **Default OpenCL = OFF for UNet**. Add a runtime probe that disables
   `useOpenCL` if Adreno is < 740 or thermal state is yellow.
2. **Keep OpenCL for upscaler + VAE decode tiles** — short-lived, < 1 s
   each, plays nicely with the watchdog.
3. **Vulkan compute** — `MNN_VULKAN=ON` is commented out in `CMakeLists.txt`
   line 84 because Adreno's Vulkan compute had wrong-result bugs in driver
   versions before AU 14.3.0.11 (mid-2025). The user's device reports
   driver `0800.49 / AU_LINUX_ANDROID_LA.VENDOR.14.3.0.11.00.00.973.839`
   which is past the fix. Worth re-enabling and testing.

## Unified-memory notes (Adreno UMA on mobile Snapdragon)

UMA gives us zero-copy between CPU and GPU (CL_MEM_USE_HOST_PTR), but:
- The mapping invalidates GPU cache on every CPU touch. If you
  read-modify-write a tensor from CPU between two GPU ops, expect the
  second GPU op to stall waiting for cache flush.
- HTP has its **own** memory pool (rpcmem-mapped DSP shared memory). The
  copy from app heap → rpcmem on each `executeUnetGraphs` call is real and
  costs ~5-10 ms per call. Mitigations: pre-allocate rpcmem-backed input
  tensors at model load and reuse pointers (this is what
  `qnn_model.h::clearCachedEmbeddings` is partly about).
- Best mental model: HTP and CPU share DRAM but cache lines, not buffers.
  Write a buffer once, hand it to one accelerator per generation.

## What's already optimal

- CPU pinning (`pin_to_perf_cores`) — keep it.
- Persistent UNet/VAE sessions — keep them.
- Pre-allocated `PipelineContext::Buffers` — keep them.
- Sequential CLIP release after encode — keep it (cuts 200+ MB peak).
- Cached jbyteArray for JNI preview callbacks — keep it.

## Things that look like wins but aren't

- **Switching UNet to OpenCL on this SoC**: slower than HTP, hurts display.
- **Multi-threading CLIP and UNet in parallel**: they share the only HTP
  context. Sequential is correct.
- **Higher `numThread` on CPU**: we already saturate the 4 A78 cores;
  including A55s causes scheduler thrashing.
- **Removing the `Memory_Low` flag**: gives marginal speed at the cost of
  hitting OOM-kill on resolutions ≥ 768.
