  The 5 Key Techniques That Make GPU Fast on Mobile

  1. Command Tape / Graph Replay (WeChat XNet-DNN)

  Record the entire decode graph ONCE. Replay with a single CPU call each token. Like CUDA Graphs but for Vulkan/OpenCL.
  - Eliminates ALL per-kernel CPU bookkeeping on repeat runs
  - Decode graph is identical every token — perfect for replay
  - Result: 7-35% faster prefill, 5-14% faster decode vs llama.cpp

  2. Tensor Virtualization (Google ML Drift)

  Decouple logical tensor indices from physical GPU memory. Different memory layouts per device (Adreno prefers X, Mali prefers Y).
  - Stage-aware kernel selection: different kernels for prefill vs decode
  - Prefill → convolution-style kernels (batch GEMM)
  - Decode → fully-connected-style kernels (GEMV)
  - Result: 5-11x over llama.cpp on Adreno

  3. GPU+NPU Concurrent Bandwidth Saturation (HeteroInfer)

  This is the killer insight:

  Single processor bandwidth: 40-45 GB/s (59-66% of 68 GB/s peak)
  GPU + NPU together:         ~60 GB/s  (88% of peak)

  No single processor saturates SoC memory bandwidth. Run GPU and NPU in parallel on split tensors:
  - Row-partition weight matrices: 75% GPU, 25% NPU
  - Result: 51 tok/s decode for 1.8B model (vs ~7 for CPU-only)

  4. Adreno CL_Image Weight Storage (MNN-LLM, Qualcomm OpenCL)

  Store quantized weights as CL_RGBA Image objects instead of buffers:
  - Exploits Adreno's texture engine L1 cache (separate from compute L1)
  - 128-bit vectorized loads per work-item
  - Layout: [l/lp, h, lp] with lp=32
  - Result: 25.3x prefill, 7.1x decode over llama.cpp

  5. NPU for Prefill, GPU for Decode (Stage-Disaggregated)

  Every framework that's fast does this:
  - Prefill → NPU (fixed-shape INT8 GEMM, up to 1600 tok/s on Dimensity 9500)
  - Decode → GPU or GPU+NPU parallel (memory-bound GEMV)
  - Attention/LayerNorm → GPU (variable shapes, float ops)
  - CPU → orchestration + activation outliers (0.1-0.3% of channels)

  Critical Finding: OpenCL > Vulkan for Adreno

  Multiple sources confirm:
  "Vulkan is NOT recommended for Adreno GPUs on Android" — users report severe performance issues and device-lost errors above batch 32. OpenCL is the recommended path.

  Qualcomm literally contributed an official OpenCL backend to llama.cpp for this reason. The key optimizations:
  - cl_qcom_onchip_global_memory extension (Adreno-specific shared memory)
  - Integer dot product extensions
  - Q4_0 --pure quantization for kernel efficiency

  The Memory Bandwidth Wall

  For decode (the bottleneck), it's all about memory bandwidth:

  SD 8 Gen 3 LPDDR5X: 68 GB/s theoretical, 61.9 GB/s measured

  350M Q4 model = ~230MB weights
    → 230MB / 45 GB/s (single GPU) = 5.1ms → 196 tok/s theoretical max
    → 230MB / 60 GB/s (GPU+NPU) = 3.8ms → 263 tok/s theoretical max

  3B Q4 model = ~1.7GB weights
    → 1.7GB / 45 GB/s = 37.8ms → 26 tok/s
    → 1.7GB / 60 GB/s = 28.3ms → 35 tok/s

  Your 2.7 t/s is 72x slower than the theoretical max for your model size. That's pure overhead.

  Part 1: What llama.cpp Vulkan Actually Does (I Was Partially Wrong)

  llama.cpp already batches ~100 ops into one vkQueueSubmit and has 13 fusion patterns. So it's NOT 160 individual submissions. The real overhead is:

  1. Per-op descriptor set updates — updateDescriptorSets() is a CPU-side call for each of ~200 ops
  2. Pipeline binding — shader context switch per op (Adreno has 2-4 shader cores vs desktop 80+)
  3. Full memory barriers — flushes ALL GPU caches between ops on tile-based Adreno
  4. No graph replay — command buffer is re-recorded fresh every single token (unlike CUDA Graphs)

    ✓ Tokenizer vocabulary

    ✗ NO compute graph
    ✗ NO operation definitions
    ✗ NO execution order
    ✗ NO hardware info
