QUESTION 1: Can we build a unified compute graph?
  ANSWER: Yes. GGUF proves it — it's just a weight container, not compute spec.
  Three major projects load same GGUF with completely different engines:
    • vLLM → CUDA kernels
    • llama.cpp → ggml backends (CPU/GPU/NPU)
    • Cactus Compute → ARM SIMD + custom NPU scheduling

QUESTION 2: What would it look like?
  ANSWER: 3-layer abstraction
    Layer 1 (IR): Model-agnostic DAG (12-15 op types: MUL_MAT, RMS_NORM, ROPE, etc.)
    Layer 2 (Lowering): Per-backend translation (Adreno OpenCL, Mali Vulkan, NPU, CPU)
    Layer 3 (Execution): Schedulers with graph replay, tensor virtualization, hetero dispatch

QUESTION 3: What to steal from each framework?
  
  Megakernel (Hazy Research):
    ✗ NOT mobile (requires 240KB shared memory, 32-64KB on mobile)
    ✓ Steal: Fusion concept + schedule reuse (but graph-based, not flat)

  FlashInfer (MLSys 2025 Best Paper):
    ✓ JIT kernel compilation + binary caching
    ✓ Composable kernel formats (different KV cache layouts)
    ✓ Steal: Parameterized kernel generation (templates)

  ML Drift (Google, CVPR 2025):
    ✓ Tensor virtualization (logical shape ≠ physical layout)
    ✓ Stage-aware kernels (prefill batch GEMM vs decode GEMV)
    ✓ Steal: Tensor virtualization layer + stage-aware registry

  HeteroInfer (Tsinghua, SOSP 2025):
    ✓ GPU+NPU concurrent execution (88% bandwidth vs 60% GPU-only)
    ✓ Unified memory mapping (zero-copy on LPDDR5)
    ✓ Predictive waiting (poll instead of block)
    ✓ Steal: Concurrent dispatch + memory mapping + polling

  llama.cpp:
    ✓ GGUF loading + multi-backend system + KV cache
    ✓ Steal: All of it (already integrated)

CRITICAL INSIGHTS
================================================================================

1. MUL_MAT is 90% of compute
   → Optimize one perfect quantized matmul kernel = solve 90% of problem
   → Perfect target: Adreno CL_Image (5-7x decode speedup from texture L1 cache)

2. No single processor saturates memory bandwidth
   GPU alone: 43 GB/s (60% of 68 GB/s LPDDR5)
   NPU alone: 43 GB/s
   GPU + NPU: 59.5 GB/s (88% of peak!)
   → GPU+NPU concurrent dispatch is killer optimization

3. Prefill vs decode are fundamentally different
   Prefill: batch GEMM (uses GPU well)
   Decode: GEMV (memory-bound, needs different kernels)
   → Stage-aware kernel selection gives 2-3x

4. OpenCL > Vulkan for Adreno (on mobile)
   Qualcomm themselves say this
   Multiple sources confirm Vulkan has performance issues on Adreno mobile
   → Use OpenCL for Adreno, Vulkan for Mali

5. Graph replay eliminates per-op CPU overhead
   CUDA Graphs (desktop) → Command tape (mobile Vulkan/OpenCL)
   Decode graph identical every token → record once, replay each token
   → +1.3x from just eliminating launch overhead

6. Tensor virtualization is portable across devices
   Same logical tensor, different physical layouts per device:
     Adreno: TEXTURE_2D (texture cache)
     Mali: NHWC (subgroup operations)
     CPU: Linear NEON
   → One abstraction, many implementations

RISK ASSESSMENT & MITIGATION
================================================================================

Risk: Kernel compilation bugs
  Likelihood: High
  Impact: Build failure
  Mitigation: Unit tests + incremental rollout (Adreno first, then Mali, CPU)

Risk: Memory layout mismatch
  Likelihood: Medium
  Impact: Numerical errors
  Mitigation: Validate every layout transformation against reference

Risk: Hardware variance (Adreno models)
  Likelihood: Medium
  Impact: Crashes on older chips
  Mitigation: Feature detection + graceful degradation to llama.cpp

Risk: NPU sync overhead dominates
  Likelihood: Low
  Impact: No speedup from GPU+NPU
  Mitigation: Profile first, only enable if >10% gain

Risk: Regression vs llama.cpp
  Likelihood: Medium
  Impact: User backlash
  Mitigation: CI/CD with perf regression tests, keep llama.cpp fallback
