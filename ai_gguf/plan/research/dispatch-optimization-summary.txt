#1 (TOP PRIORITY): OpenCL CL_Image Weight Storage
────────────────────────────────────────────────────
Expected Gain:   3.0x decode speedup (2.7 → 8.1 tok/s)
Difficulty:      MEDIUM
Effort:          2-3 weeks
Risk:            LOW (proven by MNN-LLM)
Status:          READY FOR PROTOTYPING

How it works:
  • Store quantized weights as CL_RGBA image objects (not buffers)
  • Adreno's texture engine L1: 70-85% hit rate (vs 30-40% compute L1)
  • 128-bit vectorized reads reduce memory transactions by 4x
  • Native support for Q8_0, Q4_0 quantization formats

Key Implementation:
  ✓ ggml-opencl.cpp: new kernel_mul_mv_q8_0_image() variants
  ✓ Weight layout transformation at GGUF load time
  ✓ Device capability detection (CL_DEVICE_MAX_READ_IMAGE_ARGS)
  ✓ No data layout changes; just map as image instead of buffer

#3 (VULKAN-SPECIFIC): VK_KHR_push_descriptor
────────────────────────────────────────────────────
Expected Gain:   1.15x additional speedup (10.1 → 11.6 tok/s)
Difficulty:      MEDIUM
Effort:          2-3 weeks
Risk:            MEDIUM (device compatibility fallback required)
Scope:           Vulkan only; OpenCL unaffected

How it works:
  • Write descriptors directly into command buffer (no allocation)
  • Eliminates vkAllocateDescriptorSets + vkUpdateDescriptorSets overhead
  • Saves 20-30ms per token on typical 100+ op/token workload
  • Adreno 740+ supported; fallback to descriptor pools for older devices

Implementation:
  ✓ Device capability check (vkGetPhysicalDeviceProperties2)
  ✓ Conditional code path: push descriptors vs descriptor pools
  ✓ Batch operations by access pattern (weights, activations, temps)

Files to modify:
  • /home/home/CLionProjects/llama.cpp-android/ggml/src/ggml-vulkan.cpp


#4 (ADVANCED): Command Buffer Replay (Graph Recording)
────────────────────────────────────────────────────
Expected Gain:   1.08x speedup (decode only)
Difficulty:      HIGH
Effort:          4-6 weeks
Risk:            HIGH (state management complexity)
Best for:        Decode phase (constant graph shape)

How it works:
  • Record compute graph ONCE during first token
  • Replay identical graph for each subsequent token
  • CUDA Graphs equivalent for Vulkan/OpenCL
  • Eliminates per-token command buffer reconstruction

Implementation:
  ✓ Vulkan: VK_COMMAND_BUFFER_USAGE_SIMULTANEOUS_USE_BIT
  ✓ OpenCL: cl_qcom_recordable_queues extension (Adreno)
  ✓ Separate prefill/decode graphs (different batch sizes)
  ✓ Graph state management: recording, validation, replay


#5 (ADVANCED): Barrier Optimization

Expected Gain:   1.05-1.10x speedup
Difficulty:      MEDIUM-HIGH
Effort:          3-4 weeks
Risk:            MEDIUM-HIGH (dependency analysis correctness)

CRITICAL FINDINGS
================================================================================

OpenCL > Vulkan for Adreno (3-4x speedup difference)
  • Qualcomm contributed OpenCL backend to llama.cpp specifically
  • CL_Image texture cache unavailable in Vulkan (Adreno architecture)
  • Vulkan has device-lost issues above batch size 32

Best models for tool calling (GGUF, mobile-ready):
  • SmolLM3-3B: 92.3% BFCL, Hermes <tool_call> format, Apache 2.0
  • xLAM-2-3b-fc-r: 65.7% BFCL, 55.6% multi-turn
  • Qwen3-0.6B: 0.880 judgment score, extremely cheap

GPU+NPU bandwidth saturation:
  • Single GPU: 40-45 GB/s (59-66% of 68 GB/s theoretical)
  • Single NPU: 40-45 GB/s
  • GPU+NPU parallel: 60 GB/s (88% of peak)
  • No single processor saturates LPDDR5X bandwidth
