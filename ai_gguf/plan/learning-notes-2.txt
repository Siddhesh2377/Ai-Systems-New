  Why This Works: Prompt vs Tensor

  Traditional approach (everyone else):
    System prompt says "be warm" → model MIGHT listen → model MIGHT ignore
    System prompt says "use JSON" → model MIGHT format correctly → 38% error rate
    User overwrites prompt → everything breaks

  Our approach:
    Control vectors say "be warm" → activations PHYSICALLY shift → model HAS to be warm
    Grammar says "use JSON" → invalid tokens get -inf bias → 0% error rate
    User writes anything → engine behavior unchanged, prompt is just context

  The model can't "choose" to ignore our interventions. They operate on the tensor math itself. It's like the difference between asking someone to speak French vs physically rewiring
  their brain to produce French.

1. Context Length Impact on Tool Calling

  Short answer: Grammar masking is context-independent. The model forward pass scales linearly.

  Here's the breakdown for Qwen3-0.6B at different context lengths:

  ┌───────────────────────────────┬─────────┬──────────┬──────────┐
  │           Component           │ 298 ctx │ 2048 ctx │ 8192 ctx │
  ├───────────────────────────────┼─────────┼──────────┼──────────┤
  │ Weight GEMV (bandwidth-bound) │ ~47ms   │ ~47ms    │ ~47ms    │
  ├───────────────────────────────┼─────────┼──────────┼──────────┤
  │ KV attention O(seq_len)       │ ~0.5ms  │ ~3ms     │ ~12ms    │
  ├───────────────────────────────┼─────────┼──────────┼──────────┤
  │ Grammar mask (vocab-only)     │ ~0.8ms  │ ~0.8ms   │ ~0.8ms   │
  ├───────────────────────────────┼─────────┼──────────┼──────────┤
  │ Total decode                  │ ~50ms   │ ~52ms    │ ~60ms    │
  └───────────────────────────────┴─────────┴──────────┴──────────┘

  The grammar engine operates on logits (151936 floats) — it doesn't touch KV cache or context at all. So tool calling overhead stays constant at 0.8ms regardless of context.

  Could we pipeline or GPU-offload grammar? We could run grammar masking on a separate thread while the next forward pass computes, but 0.8ms out of 50ms (1.6%) isn't worth the
  complexity. GPU would actually be slower — grammar is branch-heavy (state machine switches), which GPUs hate.

  The real context cost is the multi-step prefill. When we inject 32 tool-result tokens mid-conversation, those are prefilled at ~80 tok/s — same as initial prompt. At long context this
   stays efficient because prefill is parallelized across the sequence.

  2. Plugin Compute Graph — How it works today

  The graph is NOT JIT in the traditional sense. It's a declarative dataflow graph rebuilt every forward pass:

  build_graph() called →
    ggml_context created →
      ops added: get_rows, rms_norm, mul_mat, rope, flash_attn, etc. →
        ggml_cgraph returned →
          gallocr allocates intermediates →
            backend executes ops in dependency order

  It's rebuilt each call because the shape changes (seq_len=298 for prefill, seq_len=1 for decode, different kv_pos). But the compute kernels are pre-compiled in the backend .so files
  (ggml-cpu.so, ggml-opencl.so). Think of it like a SQL query plan — you describe WHAT to compute, the backend decides HOW.

  Currently build_graph() is hardcoded for Qwen3. To support Llama/Mistral/Gemma/Phi/etc., we need architecture plugins.

  3. Native RAG — Very doable

  Embedding models are just transformers that output vectors instead of token logits. We already have the forward pass code. The full RAG pipeline would be:

  File → Parse → Chunk → Embed → Index → Query → Retrieve → Inject into prompt

  All native C++, no Python dependency.
