SDN1 : Read this Data

<< Per-Op Vulkan Dispatch Sequence

   > The Vulkan backend records GPU commands into command buffers. For each op: allocate descriptor set, bind pipeline, set push constants, dispatch. ~200 descriptor set updates per token, each requiring CPU validation. On Adreno 750 (2-4 shader cores), pipeline switches are catastrophic.
   > // For EACH of ~100 GPU ops per token:
   >
   > // 1. Allocate descriptor set from pool
   > vkAllocateDescriptorSets(device, &allocInfo, &descSet);
   > // Pool size: 256 sets. New pool created when exhausted.
   >
   > // 2. Update descriptor set (bind buffers to shader params)
   > vkUpdateDescriptorSets(device, writeCount, writes, 0, nullptr);
   > // Up to 12 buffer bindings per kernel (parameter_count max = 12)
   >
   > // 3. Record into command buffer
   > cmd.pushConstants(layout, COMPUTE, 0, size, data);
   > cmd.bindPipeline(COMPUTE, pipeline);       // ← pipeline switch!
   > cmd.bindDescriptorSets(COMPUTE, layout, 0, {descSet}, {});
   > cmd.dispatch(wg0, wg1, wg2);               // launch compute shader
   >
   > // 4. Memory barrier between ops
   > cmd.pipelineBarrier(
   >     COMPUTE, COMPUTE,                       // src → dst stage
   >     {}, {},
   >     {bufferBarrier(SHADER_WRITE, SHADER_READ)} // ← FULL FLUSH
   > );
   > // On tile-based GPUs (Adreno/Mali): this flushes L1 tile cache!

   > << Pipeline

   > struct vk_pipeline_struct {
   >     std::string name;
   >     vk::ShaderModule shader_module;  // compiled SPIR-V
   >     vk::PipelineLayout layout;
   >     vk::Pipeline pipeline;
   >     uint32_t push_constant_size;
   >     uint32_t parameter_count;        // max 12 buffer bindings
   >     std::array3> wg_denoms; // workgroup size divisors
   >     uint32_t align;
   >     std::atomic needed;
   >     std::atomic compiled;      // lazy compilation
   > };

   > // Total compiled pipelines: 1000+ variants
   > // (mul_mat × quant_type × dims × precision × aligned/unaligned)
   > // Pipeline cache stored via VkPipelineCache


   > << Cost BreakDown

   > Descriptor set alloc+update	~200	~5 μs	~1.0 ms

   > The CL_Image opportunity: Adreno has a separate texture engine with its own L1 cache. When you store quantized weights as CL_RGBA Image2D objects, each work-item loads 128 bits (4 × 32-bit RGBA channels) in one instruction, hitting the texture cache instead of compute cache. This is THE reason MNN-LLM gets 7.1x decode over llama.cpp.

SDN2 :
   > Why llama.cpp Gets 2.7 tok/s on GPU
   > Your research doc identified the gap: theoretical 93 tok/s, actual 2.7 tok/s on Vulkan. That's 72× slower. Here's the complete bottleneck analysis — every ms accounted for.
   > Time Breakdown: One Decode Token (Vulkan, Qwen2-1.5B Q4_K_M)
   > Bottleneck	Time	% of Total	Cause
   > Weight tensor copies	~200 ms	54%	ggml_backend_tensor_copy() for EVERY weight EVERY token
   > Memory barriers	~80 ms	22%	Full L1 cache flush between every op on tile-based GPU
   > Descriptor sets	~40 ms	11%	200+ allocate/update/bind cycles
   > Pipeline switches	~25 ms	7%	Shader context switch on 2-4 ALU pipes
   > Graph rebuild	~5 ms	1%	460 tensor allocs + topo sort + scheduler
   > Actual GPU compute	~15 ms	4%	MUL_MAT + FLASH_ATTN + activations
   > Total	~365 ms → 2.7 tok/s
   > 96% of time is overhead, only 4% is useful compute. The GPU is idle most of the time, waiting for the CPU to set up the next op. This is the fundamental problem your engine rewrite must solve.
   > ▸ Deep Dive: Root Cause Analysis
   > Root cause #1: Desktop architecture assumed
   >
   > // Desktop: CPU ←PCIe→ GPU (separate memory)
   > // tensor_copy() over PCIe = necessary, ~12 GB/s
   > // GPU has 80+ cores = hides CPU setup latency
   > // VRAM bandwidth: 900+ GB/s = ops finish fast
   >
   > // Mobile: CPU + GPU share LPDDR5X (UMA)
   > // tensor_copy() = memcpy within same DRAM = WASTE
   > // GPU has 2-4 ALU pipes = can't hide latency
   > // LPDDR5X: 68 GB/s = 13× slower than desktop VRAM
   > Root cause #2: No graph replay
   >
   > // Every token rebuilds the ENTIRE command buffer
   > // But decode graph is IDENTICAL every token!
   > // Only differences: KV cache pointers, position index
   > //
   > // Solution (XNet-DNN style): Record once, replay with
   > // updated buffer offsets. Eliminates descriptor set
   > // allocation, pipeline binding, barrier setup.
   > //
   > // Adreno has cl_qcom_recordable_queues for this!
   > // Vulkan has VkCommandBuffer reuse potential
   > Root cause #3: Per-op barriers instead of graph-level scheduling
   >
   > // Current: barrier after EVERY op
   > // RMS_NORM → BARRIER → MUL_MAT → BARRIER → MUL_MAT → BARRIER → ...
   > //
   > // Better: analyze data dependencies, only barrier when needed
   > // RMS_NORM → MUL_MAT_Q → MUL_MAT_K → MUL_MAT_V → BARRIER → FLASH_ATTN
   > //          (Q,K,V are independent — can pipeline without barriers)
   > //
   > // Best: fuse entire layer into 2-3 mega-kernels
   > // MEGA_ATTN(norm+Q+K+V+rope+attn+O) → MEGA_FFN(norm+gate+up+silu+mul+down)

SDN3 : Weaknesses (Fix These)
   > Graph rebuilt every token — should record & replay
   > Scheduler assumes discrete VRAM — wasteful copies on UMA
   > Per-op Vulkan dispatch — 200+ descriptor updates/token
   > Full barriers between every op — unnecessary on UMA
   > No CL_Image weight storage — missing Adreno texture cache
   > No GPU+NPU parallel execution — single backend per split
   > No stage-aware kernels — same kernel for prefill and decode
   > No weight rearrangement — row-major from GGUF, not tiled
   > Thread pool busy-waits 50% (battery drain on mobile)
   > GGML_DEFAULT_GRAPH_SIZE=2048 (needs ~500 for mobile decode)
   > 4-copy pipeline parallelism = 2GB waste on mobile

SDN1 : Some Techniques for That other use
   > Tensor Virtualization — 37 tok/s (Gemma2-2B)
   > Google, CVPR 2025. Key idea: decouple logical tensor indices from physical GPU memory layout. A tensor with logical shape [B,H,W,C] can be stored as a 1D buffer, 2D texture, or 3D texture — the shader translates coordinates at access time. Plus stage-aware kernels: different kernel shapes for prefill (GEMM) vs decode (GEMV). 5-11× over llama.cpp on Adreno.
   > Cons
   > Google internal — not open source
   > Requires offline weight pre-processing per device
   > INT8 quantization only (no Q4_K style)
   > No NPU support — GPU only
   > No command replay optimization
