01 TOKENIZATION

Text to Token IDs

Raw text is split into sub-word tokens using Byte-Pair Encoding (BPE). The tokenizer has a fixed vocabulary (Qwen2: 151,936 tokens). Each token maps to an integer ID. The model never sees strings — only integer sequences.
Running Example: "What is gravity?"
WhatID: 1841
→
 isID: 374
→
 gravityID: 23894
→
?ID: 30
"What is gravity?" → [1841, 374, 23894, 30]
Byte-Pair Encoding builds a vocabulary bottom-up:

1. Start with all individual UTF-8 bytes (256 base tokens)
2. Count all adjacent pairs in the training corpus
3. Merge the most frequent pair into a new token
4. Repeat until vocabulary reaches target size (e.g. 151,936)

Each merge rule is stored in a merges file. At inference time, the tokenizer applies these merges greedily left-to-right.
// BPE merge example "g" + "r" → "gr" // merge #1247 "gr" + "av" → "grav" // merge #8391 "grav" + "ity" → "gravity" // merge #12044 // Result: "gravity" = single token ID 23894 // Rare words like "gravitino" → ["gravit", "ino"]
SentencePiece (used by Qwen2, LLaMA) treats text as a raw byte stream — no pre-tokenization. Uses Unigram LM or BPE internally. Key difference: spaces are encoded as ▁ (U+2581) prefix, not separate tokens.

Qwen2 uses a custom tiktoken-based tokenizer with 151,936 tokens including 151,643 regular + 293 special tokens.

02 EMBEDDINGS

Token IDs to Vectors

Each token ID indexes into an embedding matrix of shape [vocab_size × d_model]. For Qwen2-1.5B: [151,936 × 1,536]. This is a simple lookup — no math, just read row #ID from the matrix. Result: each token becomes a 1,536-dimensional float vector.

Transformers have no inherent sense of position. Token at position 0 and position 100 would produce identical representations without positional encoding. Modern LLMs use Rotary Position Embeddings (RoPE) — applied inside attention, not to embeddings directly.
RoPE(x, pos) = x · cos(pos · θ) + rotate(x) · sin(pos · θ)
Where θ_i = base^(-2i/d) and base is typically 10000 (Qwen2: 1,000,000 for long context). RoPE encodes relative position: the dot product between two RoPE'd vectors depends only on their distance, not absolute positions.

In ggml: This is the ROPE op, applied to Q and K tensors after projection but before attention. It's a per-element rotation — cheap compute, zero extra memory.

03 THE TRANSFORMER BLOCK

The Repeating Unit — N Identical Layers

A transformer is just N identical blocks stacked. Each block: RMSNorm → Attention → Residual → RMSNorm → FFN → Residual. Qwen2-1.5B has 28 blocks. Every token passes through all 28 sequentially. The residual connections (x + output) prevent gradient vanishing and allow information to flow unchanged.
Single Transformer Block — All ops visible to the GPU
Input: x [batch, seq_len, 1536]
↓
RMSNorm ggml: RMS_NORM — normalize to unit variance, multiply by learned scale γ
↓
Multi-Head Attention Q,K,V projections → RoPE → Attention → Output projection
↓ + x (residual)
RMSNorm ggml: RMS_NORM
↓
Feed-Forward Network (SwiGLU) Up + Gate projections → SiLU → multiply → Down projection
↓ + x (residual)
Output: x' [batch, seq_len, 1536] — same shape as input
RMSNorm(x) = x / √(mean(x²) + ε) × γ
Simpler than LayerNorm — no mean subtraction, no bias. Just normalize by RMS, then scale by learned weight γ (1,536 params). Epsilon ε = 1e-6 for Qwen2.

ggml op: RMS_NORM — one of the cheapest ops. Per token: 1,536 multiply, 1 sqrt, 1,536 multiply. Negligible vs matmul.
The residual stream is the core information highway. Each layer adds to it rather than replacing it:
x = x + Attention(RMSNorm(x))
x = x + FFN(RMSNorm(x))

This means early layer information survives to the end. The model can choose to "write" new information or "read" existing information at each layer. Without residuals, information from layer 0 would be destroyed by layer 5.

04 ATTENTION MECHANISM

How Tokens Look at Each Other

Attention lets each token compute a weighted combination of all previous tokens. Query = "what am I looking for?", Key = "what do I contain?", Value = "what information do I provide?". Qwen2-1.5B uses Grouped-Query Attention (GQA): 12 query heads share 2 KV heads (6:1 ratio). This cuts KV cache by 6x with minimal quality loss.
Attention Computation — The Core Formula
Attention(Q, K, V) = softmax(Q · KT / √d_k) · V
Prefill (GEMM)
Q: [seq×128] × KT: [128×seq]
= [seq × seq] attention matrix
Compute-bound: O(n² · d)
Decode (GEMV)
q: [1×128] × KT: [128×seq]
= [1 × seq] attention scores
Memory-bound: read full KV cache

For a single head (d_head = 128), processing "gravity" at position 3:
// 1. Project input → Q, K, V (MUL_MAT ops) q = x @ W_q // [1,1536] × [1536,128] → [1,128] — 197K FLOPs k = x @ W_k // [1,1536] × [1536,128] → [1,128] — 197K FLOPs v = x @ W_v // [1,1536] × [1536,128] → [1,128] — 197K FLOPs // 2. Apply RoPE to Q and K (ROPE op) q = RoPE(q, pos=3) // rotate pairs by position-dependent angle k = RoPE(k, pos=3) // 3. Append K, V to cache (VIEW + CPY ops) KV_cache[3].K = k // cache now has positions 0,1,2,3 KV_cache[3].V = v // 4. Compute attention scores (MUL_MAT) scores = q @ K_cache.T / sqrt(128) // [1,128] × [128,4] → [1,4] // scores = [0.82, -0.31, 1.47, 0.05] (raw logits) // 5. Causal mask + softmax (SOFT_MAX) weights = softmax(scores) // [0.18, 0.06, 0.72, 0.04] // "gravity" attends most to "is" (position 2) — makes sense! // 6. Weighted sum of values (MUL_MAT) output = weights @ V_cache // [1,4] × [4,128] → [1,128]
Flash Attention fuses steps 4-5-6 into a single kernel to avoid materializing the [seq × seq] attention matrix. This saves memory from O(n²) to O(n).
// ggml: FLASH_ATTN_EXT op // Algorithm (online softmax, tiled): for tile_q in tiles(Q): // outer loop over query tiles max_score = -inf sum_exp = 0 acc = zeros(d_v) for tile_kv in tiles(K, V): // inner loop over KV tiles S = tile_q @ tile_k.T / sqrt(d) // scores in SRAM apply_causal_mask(S) // Online softmax update (Milakov & Gimelshein, 2018) new_max = max(max_score, max(S)) correction = exp(max_score - new_max) sum_exp = sum_exp * correction + sum(exp(S - new_max)) acc = acc * correction + exp(S - new_max) @ tile_v output = acc / sum_exp // final normalization // Key: never materialize full [seq × seq] matrix // Vulkan: separate pipelines for F32/F16 accumulation // Supports cooperative matrix (VK_KHR_cooperative_matrix)
KV Cache: During decode, we only compute Q/K/V for the new token, but reuse K/V from all previous tokens (stored in cache).

Causal masking prevents tokens from attending to future tokens. Position 2 ("gravity") can see positions 0,1,2 but NOT position 3 ("?"). This is what makes the model autoregressive — it can only use past context.

05 FFN & ACTIVATIONS

SwiGLU — Where 88% of Compute Lives

The Feed-Forward Network is the dominant compute cost. Modern LLMs use SwiGLU (Shazeer 2020): two parallel projections (gate + up), a SiLU activation, element-wise multiply, then a down projection. For Qwen2-1.5B: 1536 → 8960 → 1536. Each decode token requires 3 × 1536 × 8960 = 41.3M multiply-adds in the FFN alone.
SwiGLU FFN — 3 weight matrices per layer
x [1, 1536]
Gate: x @ W_gate[1536×8960] → [1, 8960]
Up: x @ W_up[1536×8960] → [1, 8960]
↓
SiLU(gate) × up element-wise: [8960] ⊙ [8960] → [8960]
↓
Down: result @ W_down [8960×1536] → [1, 1536]
SiLU (Sigmoid Linear Unit) = x × σ(x). Smoother than ReLU, no dead neurons. The "gating" mechanism means the model learns which features to amplify:
FFN(x) = (SiLU(x · W_gate) ⊙ (x · W_up)) · W_down

06 PREFILL vs DECODE

The Two Phases of Inference

This is the single most important distinction for engine design. Prefill processes the entire prompt in parallel (compute-bound). Decode generates one token at a time (memory-bandwidth-bound). They need different kernels, different scheduling, different optimizations.
PREFILL
Input: All prompt tokens at once
Attention: Q[seq×d] × KT[d×seq] = GEMM
FFN: X[seq×d] × W[d×ff] = GEMM
Bottleneck: Compute (FLOPs)
Arithmetic intensity: High (~100 FLOPs/byte)
Parallelism: Massive (all tokens parallel)
GPU utilization: 70-90%

Best kernel: im2col / tiled GEMM
Optimization: Max FLOPs throughput
DECODE
Input: 1 new token
Attention: q[1×d] × KT[d×seq] = GEMV
FFN: x[1×d] × W[d×ff] = GEMV
Bottleneck: Memory bandwidth
Arithmetic intensity: Low (~1-2 FLOPs/byte)
Parallelism: Low (1 token)
GPU utilization: 5-15%

Best kernel: Vectorized GEMV / FC
Optimization: Max memory bandwidth

07 LoRA & FINE-TUNING

Training Without Training All Parameters

LoRA (Low-Rank Adaptation) freezes the original model and trains two small matrices per target layer. Instead of updating the full [d × k] weight matrix W, learn B ∈ ℝ^{d×r} and A ∈ ℝ^{r×k} where r << min(d,k). At inference: W' = W + BA. With r=16, a 1.5B model goes from 1.5B trainable params to ~4M.
LoRA Forward Pass
h = W·x + (B·A)·x = W·x + B·(A·x)
Input x [1, 1536]
↓
W (frozen)[1536×1536] — original weight
↓
A (trainable)[16×1536] — down project
↓
B (trainable)[1536×16] — up project
↓ add (merge)
Output h [1, 1536]
LoRA exploits the fact that weight updates during fine-tuning have low intrinsic rank:
ΔW = B · A where rank(ΔW) ≤ r

Alpha scaling: The LoRA output is scaled by α/r. Typical: α=32, r=16 → scale = 2.0. This controls how much the adaptation affects the output.
QLoRA (Dettmers 2023): Keep the frozen base model in 4-bit NF4 quantization, train the LoRA adapters in BF16. During forward pass:
// QLoRA forward (per layer) W_4bit = quantize_nf4(W_fp16) // done once, stored on disk W_dequant = dequantize(W_4bit) // to BF16 on-the-fly h_base = W_dequant @ x // base model pass h_lora = B @ (A @ x) // adapter pass (BF16) h = h_base + h_lora // combine // Memory: 1.5B model in NF4 ≈ 750 MB // vs FP16 ≈ 3 GB — fine-tune on 4GB VRAM!
After training, merge the adapters into the base weights for zero-overhead inference:
// Merge: one-time operation W_merged = W_original + (alpha/r) * B @ A // Then convert to GGUF: // python convert_hf_to_gguf.py --model merged_model/ --outtype q4_k_m // Result: Standard GGUF file, no LoRA overhead at runtime // The GGUF model has NO knowledge that LoRA was used
Unmerged LoRA at runtime: llama.cpp supports loading LoRA adapters separately via llama_adapter_lora_init(). This adds the BA product during MUL_MAT — slight overhead but allows hot-swapping adapters without reloading the full model.
Training loop (simplified):
for batch in dataloader: tokens = tokenize(batch.text) // [batch_size, seq_len] input_ids = tokens[:, :-1] // all but last target_ids = tokens[:, 1:] // all but first (shifted by 1) logits = model(input_ids) // forward pass → [batch, seq, vocab] loss = cross_entropy(logits, target_ids) // next-token prediction loss loss.backward() // gradients for A, B only (W frozen) optimizer.step() // AdamW update on A, B optimizer.zero_grad() // The model learns to predict the next token // Same objective as pre-training, just on your data // Typical: 1-3 epochs, lr=2e-4, batch_size=4

08 SAMPLING

Logits to Tokens — The Decision Point

After the final layer: RMSNorm → lm_head projection [d_model → vocab_size] produces a logits vector of 151,936 raw scores. Sampling converts these to a probability distribution and picks one token. This is where temperature, top-k, top-p, repetition penalty live.
Sampling Pipeline
Raw logits [151,936] — e.g. "Gravity" = 8.2, "is" = 3.1, "The" = 2.9, ...
↓
Repetition penalty Divide logits of recent tokens by penalty (e.g. 1.1)
↓
Temperature logits = logits / T — T=0.7 sharpens, T=1.5 flattens
↓
Top-K filter Keep only K highest logits (e.g. K=40), mask rest to -∞
↓
Top-P (nucleus) Sort by probability, keep smallest set summing to P (e.g. P=0.9)
↓
Softmax Convert to probabilities: p_i = exp(logit_i) / Σ exp(logit_j)
↓
Sample Random draw from distribution → Token ID → Detokenize → "Gravity"
P(token_i) = exp(logit_i / T) / Σ_j exp(logit_j / T)
T = 0.0: Always pick highest logit (greedy/argmax)
T = 0.7: Sharp distribution, mostly picks top tokens
T = 1.0: Model's native distribution
T = 1.5: Flat distribution, more random/creative

Example with logits [8.2, 3.1, 2.9]:

Top-K: Sort logits descending, keep only K largest, set rest to -∞. Prevents sampling extremely unlikely tokens.

Top-P (nucleus sampling): Sort by probability descending, find smallest set where cumulative probability ≥ P. More adaptive than Top-K — uses fewer tokens when model is confident, more when uncertain.

Combined: Apply Top-K first (hard ceiling), then Top-P within the K survivors. Typical: K=40, P=0.9 — effective candidate set is usually 5-15 tokens.
llama.cpp sampler chain (order matters!):
// llama_sampler_chain applies these in sequence: 1. penalties // repetition, frequency, presence penalty 2. dry // DRY (Don't Repeat Yourself) — suppress repeated n-grams 3. top_k // keep K candidates 4. typical_p // locally-typical sampling (information-theoretic) 5. top_p // nucleus sampling 6. min_p // minimum probability threshold (relative to top) 7. xtc // XTC sampler (exclude top choices sometimes) 8. temp // temperature scaling 9. dist // random sampling from final distribution // Grammar constraints (if enabled) are applied as a separate // sampler that masks invalid tokens to -inf before softmax. // Your LAZY grammar mode for tool calling goes here.

09 COMPLETE TOKEN LIFECYCLE & ASSESSMENT

Full Forward Pass + Pros & Cons

Here's the complete journey of one decode token through Qwen2-1.5B, with every ggml op and byte count. Plus an honest assessment of the transformer architecture.
One Decode Token: "What is gravity?" → generating "Gravity"
// ═══ INPUT ═══ token_id = 30 // "?" — last user token // ═══ EMBEDDING ═══ GET_ROWS(embed_table, [30]) // → [1, 1536] — read 6 KB // ═══ LAYER 0..27 (×28 identical) ═══ for layer in 0..28: RMS_NORM(x) // normalize — 1,536 params q = MUL_MAT(W_q, x) // [1536×1536] × [1,1536] → [1,1536] k = MUL_MAT(W_k, x) // [1536×256] × [1,1536] → [1,256] v = MUL_MAT(W_v, x) // [1536×256] × [1,1536] → [1,256] q = ROPE(q, pos) // rotary position — in-place k = ROPE(k, pos) // KV_cache[layer][pos] = {k, v} // append to cache attn_out = FLASH_ATTN_EXT(q, K, V, mask) // fused attention o = MUL_MAT(W_o, attn_out) // [1536×1536] output proj x = x + o // residual add RMS_NORM(x) // normalize for FFN gate = MUL_MAT(W_gate, x) // [1536×8960] — 7.7 MB read up = MUL_MAT(W_up, x) // [1536×8960] — 7.7 MB read ffn = SILU(gate) * up // SwiGLU activation down = MUL_MAT(W_down, ffn) // [8960×1536] — 7.7 MB read x = x + down // residual add // ═══ OUTPUT HEAD ═══ RMS_NORM(x) // final norm logits = MUL_MAT(lm_head, x) // [1536×151936] → [1, 151936] // ═══ SAMPLING ═══ token = sample(logits, T=0.7, top_p=0.9) // → ID 77091 → "Gravity" // ═══ TOTALS ═══ // Weight reads: ~730 MB (Q4_K_M) — this is the bottleneck // FLOPs: ~3.0 GFLOPs // Ops: ~460 ggml nodes // Theoretical min time: 730 MB / 68 GB/s = 10.7 ms = 93 tok/s // Actual llama.cpp: ~30-40 tok/s (55% bandwidth utilization)

Strengths

  • Massively parallelizable during training (all tokens at once)
  • Attention captures long-range dependencies (unlike RNNs)
  • Scales predictably — more params = better quality (scaling laws)
  • Architecture-agnostic: same block works for any modality
  • KV cache makes autoregressive decode efficient (no recomputation)
  • Well-understood quantization behavior (Q4 = 95%+ quality)
  • RoPE enables extrapolation beyond training context length
  • Simple to implement — no recurrence, no complex state
  • GQA reduces KV cache memory 3-8x with minimal quality loss

Weaknesses

  • O(n²) attention during prefill — quadratic in sequence length
  • Decode is memory-bandwidth-bound — GPU sits mostly idle
  • KV cache grows linearly with context — 448 MB at 32K for 1.5B
  • Must read ALL weights for EVERY token (no conditional compute)
  • No true state — "memory" is just context window + KV cache
  • Fixed compute per token regardless of difficulty
  • Prefill and decode need completely different kernels
  • Attention doesn't compose well — can't represent nested structures
  • Training requires massive data (trillions of tokens for good models)
Bottom line for your engine rewrite: The transformer's decode phase is fundamentally a memory-bandwidth exercise. Every trick in Sections 4-6 (HeteroInfer, MNN-LLM, command tapes, etc.) exists to squeeze more bandwidth or reduce the bytes that need to be read. Your custom engine should be designed from the ground up to maximize bytes/second, not FLOPs/second.
