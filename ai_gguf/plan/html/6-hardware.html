6A — SOC ARCHITECTURE

System-on-Chip: Everything on One Die

A mobile SoC packs CPU + GPU + NPU + DSP + ISP + memory controller onto a single die (or package). Everything shares the same LPDDR5X memory through a single memory controller. This is fundamentally different from desktop where CPU and GPU have separate memory pools connected by PCIe.
Snapdragon 8 Elite (2024) — Block Diagram
CPU — Oryon V2 2× Prime (4.32 GHz) + 6× Perf (3.53 GHz) — all Oryon custom
NPU — Hexagon 73 TOPS INT8, dedicated SRAM
GPU — Adreno 830 Tile-based, 2-4 ALU pipes, 4.6 TFLOPS FP16, texture units with L1 cache
DSP + ISP + Modem Spectra ISP, X80 modem, Aqstic audio
Memory Controller → LPDDR5X 68 GB/s peak bandwidth — SHARED by all processors above
Unified Memory Architecture (UMA): the defining feature of mobile SoCs.
// Desktop: Discrete memory pools // // CPU ←→ DDR5 (64-128 GB/s) // | // PCIe 4.0 x16 (32 GB/s bidirectional) // | // GPU ←→ GDDR6X/HBM (1-3 TB/s) // // To run a tensor on GPU: // 1. Allocate GPU memory (cudaMalloc) // 2. Copy tensor CPU→GPU over PCIe (32 GB/s max) // 3. Compute on GPU // 4. Copy result GPU→CPU (another PCIe transfer) // ⚠ PCIe is the bottleneck for small tensors // Mobile: Unified memory // // CPU ←→ ┐ // GPU ←→ ├→ LPDDR5X (68 GB/s shared) // NPU ←→ ┘ // // To run a tensor on GPU: // 1. Tensor already in shared memory // 2. Just tell GPU the address (zero-copy) // 3. GPU reads directly from same DRAM // ✓ No transfer cost — but bandwidth is shared
UMA trade-off for LLMs: Zero-copy is amazing for weight tensors (GPU reads model weights directly, no upload). But ALL processors share 68 GB/s bandwidth. When GPU + NPU + CPU all read weights simultaneously, they compete for the same pipe. Desktop GPU has 1 TB/s all to itself.

6B — MEMORY HIERARCHY

Cache Lines, DRAM, and the Bandwidth Wall

LLM decode is memory-bandwidth-bound, not compute-bound. Every token requires reading the entire model (weights + KV cache) from DRAM. Understanding the memory hierarchy explains why decode is slow and what you can optimize.

Cache line = 64 bytes. The minimum unit the CPU reads from memory.
// Cache line: 64 bytes on all modern ARM and x86 // When CPU reads a single byte, it loads 64 bytes // For Q4_0 quantization (4.5 bits per weight): // One block = 18 bytes (2B scale + 16B data = 32 weights) // One 64-byte cache line = 3.5 blocks ≈ 112 weights // For Q8_0 quantization (8.5 bits per weight): // One block = 34 bytes (2B scale + 32B data = 32 weights) // One 64-byte cache line ≈ 1.88 blocks ≈ 60 weights // For FP16 (16 bits per weight): // One 64-byte cache line = 32 weights // Key insight: Q4_0 reads 3.5× more weights per cache line // This is exactly why quantization helps — not because // of reduced compute, but because of fewer DRAM reads
LLM decode reads each weight exactly once per token. For Qwen2-1.5B Q4_0: ~900 MB of weights read per token. At 68 GB/s: 900 MB / 68 GB/s = 13.2 ms/token = 75.7 tok/s theoretical max. With overhead: ~30-40 tok/s achievable.
Cache line alignment matters:
// Aligned access: tensor starts on 64-byte boundary // → one cache line fetch per 64 bytes // Misaligned access: tensor starts at offset 48 // → first 16 bytes from line N, next 48 from line N+1 // → 2 cache line fetches for 64 bytes of data // → 2× memory bandwidth wasted // GGUF enforces 32-byte alignment (not 64) // This means ~50% of tensors may cross cache line boundaries // Cactus: separate files = OS page-aligned = always aligned
The roofline model for LLM decode:
tok/s = memory_bandwidth / bytes_per_token
// Qwen2-1.5B model at different quantization levels: // // Q4_0: ~900 MB weights + KV cache reads // Q8_0: ~1.6 GB weights + KV cache reads // FP16: ~3.0 GB weights + KV cache reads // On Snapdragon 8 Elite (68 GB/s LPDDR5X): // Weights KV (256 ctx) Total tok/s // Q4_0: 900 MB + ~50 MB = 950 MB 71.5 // Q8_0: 1600 MB + ~50 MB = 1650 MB 41.2 // FP16: 3000 MB + ~100 MB = 3100 MB 21.9 // On desktop RTX 4090 (1008 GB/s GDDR6X): // Q4_0: 950 MB / 1008 GB/s = 1061 tok/s // These are theoretical maximums — real numbers are lower // The gap: 68 GB/s vs 1008 GB/s = 14.8× bandwidth difference // That's why desktop gets 100+ tok/s and mobile gets 30-40
KV cache grows with context length. At 2048 tokens with Qwen2-1.5B Q8_0 KV: KV size = 2 × 28 layers × 2 heads × 2048 × 128 dim × 1 byte = 29 MB. Small for short contexts. But at 32K tokens: 460 MB — nearly half the weight size. This is why KV cache quantization and sliding window matter.

6C — CPU: big.LITTLE AND SIMD

How ARM Cores Process Tensors

Mobile CPUs use big.LITTLE (or DynamIQ): a mix of high-performance and efficiency cores. LLM inference wants the big cores for NEON/DOTPROD/I8MM SIMD instructions. The efficiency cores are useless for matmul — too slow.

How a single NEON matmul processes one output element:
// Q4_0 GEMV: y[m] = W[m,:] · x[:] // W is quantized Q4_0, x is FP16 // Step 1: Load 32 Q4_0 weights (18 bytes = 1 block) // block_q4_0 = { float16 scale; uint8_t qs[16]; } // Each uint8 holds 2 weights: low nibble + high nibble int8x16_t raw = vld1q_u8(&block.qs[0]); int8x16_t lo = vandq_u8(raw, vdupq_n_u8(0x0F)); // low nibbles int8x16_t hi = vshrq_n_u8(raw, 4); // high nibbles // Subtract 8 to center around zero (unsigned → signed) lo = vsubq_s8(lo, vdupq_n_s8(8)); hi = vsubq_s8(hi, vdupq_n_s8(8)); // Step 2: Load 32 FP16 input values, convert to INT8 // (or compute in FP32 — depends on precision needed) // Step 3: Dot product (with DOTPROD extension) int32x4_t sum = vdotq_s32(sum, lo_chunk, x_chunk); // SDOT: 4 pairs of INT8 → 4 INT32 accumulates in 1 cycle // Without DOTPROD: need 4 multiplies + 3 adds = 7 cycles // Step 4: Scale by block scale factor float result = vaddvq_s32(sum) * (float)block.d;
Throughput comparison per cycle:
// Base NEON (ARMv8.0): 4 INT8 multiplies → 2 cycles = 2 ops/cycle // DOTPROD (ARMv8.2): 16 INT8 multiplies → 1 cycle = 16 ops/cycle (8×) // I8MM (ARMv8.6): 64 INT8 multiplies → 1 cycle = 64 ops/cycle (32×) // (SMMLA: 2×8 × 8×1 matrix multiply) // SME (ARMv9.2): Outer product accumulate, scales with vector length // On Apple M4: ~256 INT8 ops/cycle
Thread affinity is critical on mobile:
// Problem: Android scheduler may put LLM threads on LITTLE cores // LITTLE core (A520): ~1/4 the NEON throughput of big core // Solution: Pin inference threads to big cores // On Linux/Android: cpu_set_t mask; CPU_ZERO(&mask); // Snapdragon 8 Elite: cores 0-1 = Prime, 2-7 = Perf for (int i = 0; i < 8; i++) // Use all Oryon cores CPU_SET(i, &mask); sched_setaffinity(0, sizeof(mask), &mask); // llama.cpp approach: ggml_threadpool with affinity mask // Problem: it uses ALL cores including LITTLE ones // LITTLE cores are slower → they become stragglers // Other threads wait for slowest core → worse than fewer threads // Better approach: only use big cores // 2 Prime + 6 Perf = 8 threads on fast cores // Skip 4 LITTLE cores entirely
llama.cpp's thread pool uses busy-waiting by default. Each worker thread spins in a tight loop checking for work. On mobile, this wastes battery and generates heat even when idle. Better: use futex/condition variable for sleep/wake.
// ARM DynamIQ power states: // // C0: Active — full speed, full power // C1: WFI (Wait For Interrupt) — core clock gated // Wake: ~1 μs (essentially free) // C2: Retention — L1 cache powered, core off // Wake: ~50 μs // C3: Power collapse — everything off // Wake: ~500 μs (L1 cache lost, refill needed) // For LLM decode (one token every ~25-30ms): // Between tokens, cores enter C1 or C2 // C3 takes too long to recover → avoid by keeping thread alive // DVFS (Dynamic Voltage and Frequency Scaling): // Android governor adjusts frequency based on load // LLM inference = bursty: high load during compute, idle between // Governor may not ramp up fast enough // // Hack: set performance governor during inference // echo "performance" > /sys/devices/.../cpufreq/scaling_governor // (requires root — most apps can't do this)

6D — MOBILE GPU: TILE-BASED RENDERING

Adreno, Mali, PowerVR — Not Desktop GPUs

Mobile GPUs are Tile-Based Deferred Rendering (TBDR) architectures — designed for graphics, not compute. They split the screen into tiles and process each tile using fast on-chip SRAM. For compute (LLM matmul), this tile architecture is both a blessing and a curse.
Mobile GPU Architecture (Adreno 830)
Shader Processors (2-4 ALU pipes) ~256 ALUs total, FP16/FP32/INT8, wave size 64 (Adreno) or 16 (Mali)
Texture Units + L1 Cache Adreno: 32KB L1 per pipe, optimized for 2D image reads (CL_Image!)
Tile Memory (GMEM) 1-4 MB on-chip SRAM, 10× faster than DRAM
Shared LPDDR5X Same DRAM as CPU/NPU — 68 GB/s total shared
How tile-based rendering works and why it matters for compute:
// Desktop GPU (Immediate Mode Rendering — IMR): // 1. For each triangle: // - Transform vertices // - Rasterize to pixels // - Shade pixels → write to framebuffer in DRAM // Every pixel write goes to DRAM → high bandwidth // OK because desktop has 1 TB/s GDDR6X // Mobile GPU (Tile-Based Deferred Rendering — TBDR): // 1. Bin: sort ALL triangles into screen tiles (16×16 or 32×32) // 2. For each tile: // - Load tile from DRAM → on-chip GMEM (1-4 MB) // - Rasterize + shade all triangles in tile // - ALL reads/writes hit GMEM (10× faster than DRAM) // - Write final tile back to DRAM // Massive bandwidth savings — only 2 DRAM transfers per tile // For compute (LLM matmul): // ✓ GMEM acts as a fast scratchpad for tile-sized chunks // ✓ If you tile your matmul to fit GMEM, inner loop is fast // ✗ But compute dispatches bypass tile binning // ✗ Each compute dispatch has ~0.1-0.5ms CPU-side overhead // ✗ For decode (one token), dispatch overhead dominates
MNN-LLM's key insight: use CL_Image2D to exploit texture cache.
// Adreno GPU has specialized texture units with L1 cache // Designed for: read texture pixel → filter → output // This hardware path is separate from the compute path // CL_Buffer (standard): // → Read via general memory system // → Competes with compute for L2 cache // → Sequential access pattern // CL_Image2D (texture): // → Read via texture unit → dedicated L1 cache (32KB) // → 128-bit (4×FP32) vectorized reads per cycle // → Hardware handles 2D tiling automatically // → CL_RGBA format: 4 values per pixel = natural vectorization // MNN-LLM weight layout: [l/lp, h, lp] // l = total elements, lp = 32 (pack factor) // h = number of heads // Stored as 2D image: width = l/lp, height = h × lp // Each read_imagef() gets 4 weights in one cycle // Result: 5-7× faster weight reads on Adreno // This is why MNN-LLM is 7.1× faster than llama.cpp
Not all mobile GPUs benefit equally. Adreno has the largest L1 texture cache (32KB per pipe). Mali's texture cache is smaller (~8-16KB). PowerVR has good texture units but different tiling. This trick is most effective on Qualcomm Snapdragon.
The 96% overhead problem (from llama.cpp Vulkan analysis):
// llama.cpp: one decode token on Vulkan (Adreno) // Total time: ~4 ms // // Breakdown: // GPU compute (actual matmul): 0.16 ms (4%) // CPU-side overhead: 3.84 ms (96%) // ├── vkAllocateDescriptorSets: 0.8 ms // ├── vkUpdateDescriptorSets: 0.5 ms (×200) // ├── vkCmdBindPipeline: 0.3 ms // ├── vkCmdBindDescriptorSets: 0.4 ms // ├── vkCmdPipelineBarrier: 0.6 ms // ├── vkCmdCopyBuffer: 0.5 ms (tensor copies!) // ├── vkQueueSubmit: 0.3 ms // └── vkWaitForFences: 0.34 ms // // Result: 4 ms/token = 250 tok/s theoretical // But most of that is overhead, not useful compute // Actual GPU utilization: ~4% // Fix strategies: // 1. Command tape replay (XNet-DNN): record once, replay // 2. Pre-allocated descriptor pools (reduce alloc to ~0) // 3. Pipeline caching (VkPipelineCache) // 4. Batch dispatches (fewer submits per token) // 5. cl_qcom_recordable_queues (Adreno-specific)

6E — NPU AND DSP

Neural Processing Units — Promise vs Reality

Every SoC vendor ships an NPU: Qualcomm Hexagon, Google TPU, MediaTek APU, Apple ANE, Samsung dual-NPU. They promise 30-70+ TOPS at INT8. But for LLM inference, NPUs are complicated — high TOPS doesn't mean high tok/s.

Why 73 TOPS doesn't mean 73 TOPS for LLMs:
// NPU TOPS = peak theoretical at INT8 // Assumes: 100% ALU utilization, perfect data reuse // This happens for: CNN (3×3 convolutions), image classification // LLM decode reality: // Operation: y[M] = W[M×N] × x[N] (GEMV — one vector) // Data reuse ratio: N reads, M×N weights, but only 1 vector // Arithmetic intensity: ~1 op per byte (bandwidth-bound) // At 1 op/byte and 68 GB/s bandwidth: // Max useful compute = 68 GOPS (billions of ops/sec) // NPU has 73 TOPS = 73,000 GOPS // Utilization: 68 / 73,000 = 0.09% // // The NPU is 99.91% idle waiting for memory
Additional NPU problems for LLMs:
// 1. HIGH DISPATCH LATENCY // NPU dispatch: 2-5 ms per operation (via NNAPI/QNN) // For 28 layers × 7 ops/layer = 196 dispatches per token // 196 × 3 ms = 588 ms overhead alone → 1.7 tok/s // 2. FIXED GRAPH COMPILATION // NPU requires pre-compiled computation graph // Graph is compiled for fixed shapes (e.g., seq_len=1) // Changing context length → recompile (~seconds) // Dynamic KV cache = constant shape changes // 3. LIMITED OP SUPPORT // RoPE? Often not natively supported → falls back to CPU // Custom attention? Not supported → falls back // Fallback = data transfer CPU↔NPU = more overhead // 4. QUANTIZATION MISMATCH // NPU wants symmetric INT8 with per-tensor scales // GGUF uses per-block scales (32 or 256 elements) // Need format conversion → extra memory + compute
HeteroInfer's insight: NPUs ARE useful — but only for their separate memory bandwidth, not their compute. Run simple GEMV on NPU to use its memory port, not its ALUs. This gives 25% more total bandwidth without using compute at all.
Qualcomm Hexagon — the most accessible NPU on Android:

Public API via NNAPI is limited. // QNN API flow: // 1. QnnBackend_create() — initialize Hexagon runtime // 2. QnnGraph_create() — define computation graph // 3. QnnGraph_addNode() — add ops (matmul, etc.) // 4. QnnGraph_finalize() — compile graph for hardware // ↑ This step takes 1-10 seconds for LLM layers // 5. QnnGraph_execute() — run inference // 6. Repeat step 5 per token // Your ai_gguf status: nativeSetHexagonConfig() scaffolded // but Hexagon backend commented out (needs QNN SDK to build)

6F — TOKEN JOURNEY THROUGH HARDWARE

One Token, Every Layer of Silicon

Follow a single decode token through Qwen2-1.5B Q4_0 on Snapdragon 8 Elite. Every tensor read, every cache line, every NEON instruction.
Token #257: Generating "gravity" — Hardware Journey
1. Token ID → Embedding Lookup Token 26521 ("grav") → read row 26521 from embed_tokens [151936 × 1536]
= 1536 × 2 bytes (FP16) = 3072 bytes = 48 cache lines from DRAM (~80 ns each)
↓
2. For each of 28 layers: RMSNorm Read 1536 norm weights (3 KB) + compute: x_norm = x / sqrt(mean(x^2) + eps) * w
~48 cache lines. NEON: vfmaq_f32 for multiply-accumulate, vaddvq_f32 for reduction
↓
3. Q/K/V Projections (the big reads) Q: W_q[1536×1536] × x[1536] → read ~1.2 MB Q4_0 weights (18,750 cache lines!)
K: W_k[256×1536] × x → 200 KB. V: W_v[256×1536] × x → 200 KB. GQA: 2 KV heads.
↓
4. RoPE (Rotary Position Encoding) Rotate Q and K by position 257. Read precomputed sin/cos table (256 bytes).
Pure compute: complex multiply. Tiny cost — ~100 NEON ops per head.
↓
5. Attention: Q × K^T → softmax → × V Read KV cache: K[257×128×2] + V[257×128×2] per head = 131 KB per head (Q8_0 cache)
12 Q heads × 2 KV heads (GQA) = each KV head shared by 6 Q heads. ~2000 cache lines.
↓
6. Output Projection + FFN W_o[1536×1536] × attn_out → 1.2 MB read. Then FFN: gate[4096×1536] + up[4096×1536]
→ SwiGLU → down[1536×4096]. FFN reads: 3 × ~3.2 MB = ~9.6 MB Q4_0. The biggest cost!
↓
7. Repeat 28× → Final RMSNorm → LM Head LM head: W_lm[151936×1536] × x → ~138 MB Q4_0 read. Produces 151936 logits.
Total per token: ~900 MB read from DRAM. At 68 GB/s: 13.2 ms minimum.
↓
8. Sample → "ity" (token 488) Temperature scaling → top-p filtering → multinomial sample → decode to text.
Negligible compute. Append new K,V to cache (quantize to INT8 before storing).

6I — THERMAL WALL

The Physics You Can't Optimize Away

Mobile SoCs have a 5-10W thermal envelope. LLM inference at full speed consumes 3-5W. After 30-60 seconds of sustained inference, the SoC hits thermal throttling and clocks down 20-40%. This is physics — no software can fix it.

SUMMARY

Mobile vs Desktop — Pros and Cons

Mobile Pros

  • UMA — zero-copy tensor sharing between CPU/GPU/NPU
  • No PCIe bottleneck — all processors see same memory
  • Low power — 5W vs 450W = 90× more efficient per Watt
  • Always available — in your pocket, no server needed
  • Privacy — data never leaves device
  • Low latency for small models — no network round trip
  • Multiple processors to exploit (CPU+GPU+NPU+DSP)
  • ARM NEON/DOTPROD/I8MM — excellent INT8 throughput
  • Texture cache trick (CL_Image) — unique to mobile GPUs

Mobile Cons

  • 68 GB/s vs 1 TB/s — 15× less memory bandwidth
  • Thermal throttling — 40% performance drop after 60s
  • Shared bandwidth — all processors compete for 68 GB/s
  • Small models only — 0.5B to 3B params (max 7B with Q4)
  • GPU dispatch overhead — 96% of time wasted on Vulkan
  • NPU limited — high latency, fixed shapes, poor op coverage
  • No CUDA — Vulkan/OpenCL have worse tooling and drivers
  • Battery drain — sustained inference kills battery life
  • Fragmentation — 100+ SoCs with different capabilities

Desktop Pros

  • 1 TB/s+ memory bandwidth (GDDR6X/HBM3)
  • No thermal throttling — sustained performance forever
  • CUDA — best ML tooling, libraries, documentation
  • Large models — 70B+ params with quantization
  • Dedicated VRAM — no bandwidth sharing
  • Tensor cores — hardware matrix multiply acceleration
  • Mature ecosystem — ONNX, TensorRT, vLLM, etc.
  • Consistent hardware — fewer compatibility issues

Desktop Cons

  • PCIe bottleneck — 32 GB/s between CPU and GPU
  • No UMA — must copy tensors to GPU VRAM
  • 450W power draw — expensive, needs cooling
  • Not portable — requires wall power
  • GPU cost — $1,500+ for inference-grade card
  • VRAM limits — 24GB (4090), 80GB (H100), model must fit
  • Network dependency — if cloud-hosted, adds latency
  • Privacy concerns — data on server infrastructure
The bottom line for your engine: Mobile hardware CAN deliver 30-60 tok/s for 1.5B models — but only with mobile-specific optimizations. Desktop techniques (just throw CUDA at it) don't work here. Your engine needs: CL_Image weight storage, command tape replay, GPU+NPU parallelism, stage-aware kernels, and thermal-aware scheduling. The hardware is capable. The software (llama.cpp) just doesn't exploit it.
