02 GGML COMPUTE GRAPH

Building the Op DAG Every Token

For every token, llama.cpp constructs a new compute graph — a directed acyclic graph of ~460 ggml operations. Each node is a ggml_tensor with an op type, shape, and source pointers. The graph is topologically sorted and handed to the backend scheduler. This is rebuilt from scratch every single token.
ggml_cgraph — The Core Data Structure
struct ggml_cgraph { size_t size; // allocated capacity size_t n_nodes; // ~460 for Qwen2-1.5B decode size_t n_leafs; // input/weight tensors struct ggml_tensor ** nodes; // topologically sorted ops struct ggml_tensor ** leafs; // leaf tensors (inputs/params) struct ggml_tensor ** grads; // gradient tensors (training only) }; struct ggml_tensor { enum ggml_type type; // Q4_K, Q8_0, F16, F32... struct ggml_backend_buffer * buffer; int64_t ne[4]; // shape: [d0, d1, d2, d3] size_t nb[4]; // strides in bytes enum ggml_op op; // MUL_MAT, ADD, ROPE, FLASH_ATTN_EXT... int32_t op_params[64]; // op-specific parameters struct ggml_tensor * src[10]; // source tensors };
// llama-graph.cpp — one decode token for Qwen2-1.5B // Total: ~460 nodes = 28 layers × ~16 ops/layer + embedding + output GET_ROWS(token_embd, input_ids) // 1 op: embedding lookup for layer = 0..28: RMS_NORM(x, attn_norm) // 1 op q = MUL_MAT(attn_q, norm_x) // 1 op — biggest cost k = MUL_MAT(attn_k, norm_x) // 1 op v = MUL_MAT(attn_v, norm_x) // 1 op q = RESHAPE(q, [128, 12, 1]) // 1 op — reshape to heads k = RESHAPE(k, [128, 2, 1]) // 1 op q = ROPE(q, positions) // 1 op — rotary embeddings k = ROPE(k, positions) // 1 op CPY(k, kv_cache_k[layer]) // 1 op — write to KV cache CPY(v, kv_cache_v[layer]) // 1 op attn = FLASH_ATTN_EXT(q, K, V, mask) // 1 op — fused attention o = MUL_MAT(attn_output, attn) // 1 op x = ADD(x, o) // 1 op — residual RMS_NORM(x, ffn_norm) // 1 op gate = MUL_MAT(ffn_gate, norm_x) // 1 op — 7.7 MB weight read up = MUL_MAT(ffn_up, norm_x) // 1 op — 7.7 MB weight read SILU(gate) // 1 op MUL(gate, up) // 1 op down = MUL_MAT(ffn_down, gated) // 1 op — 7.7 MB weight read x = ADD(x, down) // 1 op — residual RMS_NORM(x, output_norm) // 1 op: final norm logits = MUL_MAT(output, x) // 1 op: lm_head projection
CRITICAL: This graph is rebuilt every token. That's ~460 ggml_tensor allocations, topology sort, and backend scheduling — all on the CPU hot path. XNet-DNN's "command tape" eliminates this by recording once and replaying.

03 BACKEND DISPATCH

The ggml_backend_i Interface

Every backend implements a vtable of function pointers. The scheduler splits the graph across backends, copies tensors between them, and calls graph_compute() on each. This is where the desktop-vs-mobile performance gap begins — the scheduler was designed for discrete GPUs with separate VRAM.
struct ggml_backend_i { // Identity const char * (*get_name)(ggml_backend_t backend); void (*free)(ggml_backend_t backend); // Tensor I/O (async versions for overlapping) void (*set_tensor_async)(backend, tensor, data, offset, size); void (*get_tensor_async)(backend, tensor, data, offset, size); bool (*cpy_tensor_async)(backend_src, backend_dst, src, dst); // Synchronization void (*synchronize)(ggml_backend_t backend); // Graph execution enum ggml_status (*graph_compute)(backend, cgraph); enum ggml_status (*graph_compute_async)(backend, cgraph); // Pre-compiled plans (key for replay optimization) ggml_backend_graph_plan_t (*graph_plan_create)(backend, cgraph); void (*graph_plan_free)(backend, plan); enum ggml_status (*graph_plan_compute)(backend, plan); // Events for multi-stream synchronization void (*event_record)(backend, event); void (*event_wait)(backend, event); // Graph optimization (your addition) void (*graph_optimize)(backend, cgraph); };
// ggml_backend_sched_split_graph() — the 5-pass algorithm // Location: ggml-backend.cpp:923-1283 // Pass 1: Assign backends to each op based on support + priority // Pass 2: Expand partitions (merge adjacent ops on same backend) // Pass 3: Create graph splits at backend boundaries // Pass 4: Allocate tensor copies for cross-backend transfers // Pass 5: Execute splits in order // THE PROBLEM (ggml-backend.cpp:1443-1620): // ggml_backend_sched_compute_splits() does: for each split: for each input tensor crossing backend boundary: ggml_backend_tensor_copy(input, input_cpy) // ← EVERY TOKEN! // This is SYNCHRONOUS, blocks thread, malloc fallback // On UMA (mobile): this copies data that's ALREADY accessible! backend->graph_compute(split_graph) // execute this split
On desktop (discrete GPU): copies go over PCIe, this is necessary.
On mobile (UMA/shared memory): GPU and CPU share LPDDR5X. These copies are WASTE. This is the "2.3 t/s killer" identified in your llama.cpp audit. GGML_SCHED_MAX_COPIES=4 means 4 copies of weights = 2GB on mobile!

04 VULKAN BACKEND

Command Buffers, Descriptors, & Barriers

The Vulkan backend records GPU commands into command buffers. For each op: allocate descriptor set, bind pipeline, set push constants, dispatch. ~200 descriptor set updates per token, each requiring CPU validation. On Adreno 750 (2-4 shader cores), pipeline switches are catastrophic.
Per-Op Vulkan Dispatch Sequence
// For EACH of ~100 GPU ops per token: // 1. Allocate descriptor set from pool vkAllocateDescriptorSets(device, &allocInfo, &descSet); // Pool size: 256 sets. New pool created when exhausted. // 2. Update descriptor set (bind buffers to shader params) vkUpdateDescriptorSets(device, writeCount, writes, 0, nullptr); // Up to 12 buffer bindings per kernel (parameter_count max = 12) // 3. Record into command buffer cmd.pushConstants(layout, COMPUTE, 0, size, data); cmd.bindPipeline(COMPUTE, pipeline); // ← pipeline switch! cmd.bindDescriptorSets(COMPUTE, layout, 0, {descSet}, {}); cmd.dispatch(wg0, wg1, wg2); // launch compute shader // 4. Memory barrier between ops cmd.pipelineBarrier( COMPUTE, COMPUTE, // src → dst stage {}, {}, {bufferBarrier(SHADER_WRITE, SHADER_READ)} // ← FULL FLUSH ); // On tile-based GPUs (Adreno/Mali): this flushes L1 tile cache!
struct vk_pipeline_struct { std::string name; vk::ShaderModule shader_module; // compiled SPIR-V vk::PipelineLayout layout; vk::Pipeline pipeline; uint32_t push_constant_size; uint32_t parameter_count; // max 12 buffer bindings std::array3> wg_denoms; // workgroup size divisors uint32_t align; std::atomic needed; std::atomic compiled; // lazy compilation }; // Total compiled pipelines: 1000+ variants // (mul_mat × quant_type × dims × precision × aligned/unaligned) // Pipeline cache stored via VkPipelineCache

05 OPENCL BACKEND

Kernel Compilation & Adreno Optimization

OpenCL on Adreno has less overhead than Vulkan (no descriptor sets, simpler dispatch). Your llama.cpp-android has 80+ specialized kernels. Binary caching keyed on device fingerprint. But: no CL_Image usage — weights stored as plain cl_mem buffers, missing the Adreno texture engine optimization that MNN-LLM uses for 7x speedup.
// Kernel cache: hash(device_name + driver_version + compile_opts + source) // Cache dir set via nativeSetGPUCacheDir() or GGML_OPENCL_CACHE_DIR // Format: ggml_cl_{hash}.bin // Dispatch is simpler than Vulkan: clSetKernelArg(kernel, 0, sizeof(cl_mem), &buf_a); clSetKernelArg(kernel, 1, sizeof(cl_mem), &buf_b); clSetKernelArg(kernel, 2, sizeof(cl_mem), &buf_out); clSetKernelArg(kernel, 3, sizeof(int), &M); clEnqueueNDRangeKernel(queue, kernel, 2, NULL, global, local, 0, NULL, NULL); // No descriptor sets, no pipeline binding, no barriers needed // OpenCL driver handles dependencies via in-order queue // UMA optimization (your code): clCreateBuffer(ctx, CL_MEM_USE_HOST_PTR, size, host_ptr, &err); // Zero-copy: GPU reads directly from LPDDR5X, no copy needed

The CL_Image opportunity: Adreno has a separate texture engine with its own L1 cache. When you store quantized weights as CL_RGBA Image2D objects, each work-item loads 128 bits (4 × 32-bit RGBA channels) in one instruction, hitting the texture cache instead of compute cache. This is THE reason MNN-LLM gets 7.1x decode over llama.cpp.

06 CPU BACKEND

ARM NEON, DOTPROD, I8MM, SVE

The CPU backend uses hand-written SIMD intrinsics for quantized dot products. The hot function: ggml_vec_dot_q4_0_q8_0 — computes the dot product of a Q4_0 weight row with a Q8_0 activation vector using 128-bit NEON registers. Your build with GGML_CPU_ALL_VARIANTS=ON produces 7 .so variants for runtime CPU feature detection.
ARM NEON Q4_0 × Q8_0 Dot Product — The Hottest Loop
// For each block of 32 quantized values: // 1. Load 16 bytes of Q4_0 weights (32 × 4-bit packed) uint8x16_t v0 = vld1q_u8(x[i].qs); // 128-bit load // 2. Extract low and high nibbles int8x16_t lo = vandq_u8(v0, mask_0F); // low 4 bits int8x16_t hi = vshrq_n_u8(v0, 4); // high 4 bits // 3. Subtract bias (Q4_0 stores 0..15, need -8..7) lo = vsubq_s8(lo, bias_8); // lo - 8 hi = vsubq_s8(hi, bias_8); // hi - 8 // 4. Load Q8_0 activations (32 × int8) int8x16_t y_lo = vld1q_s8(y[i].qs); // first 16 int8x16_t y_hi = vld1q_s8(y[i].qs + 16); // next 16 // 5. DOTPROD or I8MM accumulate #if __ARM_FEATURE_MATMUL_INT8 // I8MM: 8×8→32-bit matrix multiply (2× throughput vs DOTPROD) sum = vmmlaq_s32(sum, lo, y_lo); // fused matmul-acc sum = vmmlaq_s32(sum, hi, y_hi); #elif __ARM_FEATURE_DOTPROD // DOTPROD: 4-element dot product → 32-bit accumulate sum = vdotq_s32(sum, lo, y_lo); // 4×int8 → int32 sum = vdotq_s32(sum, hi, y_hi); #else // Basic NEON: multiply-widen-accumulate (slowest path) int16x8_t p = vmull_s8(vget_low_s8(lo), vget_low_s8(y_lo)); sum = vpadalq_s16(sum, p); #endif // 6. Scale by block scales float scale = FP16_TO_FP32(x[i].d) * FP16_TO_FP32(y[i].d); result += vaddvq_s32(sum) * scale;

07 MOBILE BOTTLENECKS

Why llama.cpp Gets 2.7 tok/s on GPU

Your research doc identified the gap: theoretical 93 tok/s, actual 2.7 tok/s on Vulkan. That's 72× slower. Here's the complete bottleneck analysis — every ms accounted for.
Time Breakdown: One Decode Token (Vulkan, Qwen2-1.5B Q4_K_M)
BottleneckTime% of TotalCause
Weight tensor copies~200 ms54%ggml_backend_tensor_copy() for EVERY weight EVERY token
Memory barriers~80 ms22%Full L1 cache flush between every op on tile-based GPU
Descriptor sets~40 ms11%200+ allocate/update/bind cycles
Pipeline switches~25 ms7%Shader context switch on 2-4 ALU pipes
Graph rebuild~5 ms1%460 tensor allocs + topo sort + scheduler
Actual GPU compute~15 ms4%MUL_MAT + FLASH_ATTN + activations
Total~365 ms → 2.7 tok/s
96% of time is overhead, only 4% is useful compute. The GPU is idle most of the time, waiting for the CPU to set up the next op. This is the fundamental problem your engine rewrite must solve.
Root cause #1: Desktop architecture assumed
// Desktop: CPU ←PCIe→ GPU (separate memory) // tensor_copy() over PCIe = necessary, ~12 GB/s // GPU has 80+ cores = hides CPU setup latency // VRAM bandwidth: 900+ GB/s = ops finish fast // Mobile: CPU + GPU share LPDDR5X (UMA) // tensor_copy() = memcpy within same DRAM = WASTE // GPU has 2-4 ALU pipes = can't hide latency // LPDDR5X: 68 GB/s = 13× slower than desktop VRAM
Root cause #2: No graph replay
// Every token rebuilds the ENTIRE command buffer // But decode graph is IDENTICAL every token! // Only differences: KV cache pointers, position index // // Solution (XNet-DNN style): Record once, replay with // updated buffer offsets. Eliminates descriptor set // allocation, pipeline binding, barrier setup. // // Adreno has cl_qcom_recordable_queues for this! // Vulkan has VkCommandBuffer reuse potential
Root cause #3: Per-op barriers instead of graph-level scheduling
// Current: barrier after EVERY op // RMS_NORM → BARRIER → MUL_MAT → BARRIER → MUL_MAT → BARRIER → ... // // Better: analyze data dependencies, only barrier when needed // RMS_NORM → MUL_MAT_Q → MUL_MAT_K → MUL_MAT_V → BARRIER → FLASH_ATTN // (Q,K,V are independent — can pipeline without barriers) // // Best: fuse entire layer into 2-3 mega-kernels // MEGA_ATTN(norm+Q+K+V+rope+attn+O) → MEGA_FFN(norm+gate+up+silu+mul+down)

08 LLAMA.CPP: PROS & CONS

Assessment for Your Engine Rewrite

Strengths (Keep These)

  • GGUF loader — excellent, well-tested, mmap support
  • Quantized dot products — NEON/I8MM kernels are highly optimized
  • Flash attention algorithm — correct, numerically stable
  • Architecture support — 30+ model types from GGUF metadata
  • Tokenizer — complete BPE/SentencePiece implementation
  • Sampler chain — comprehensive, well-ordered
  • Backend abstraction — clean interface for adding new backends
  • KV cache management — grow/shrink/quantize/persist
  • Dynamic CPU variant loading — runtime feature detection

Weaknesses (Fix These)

  • Graph rebuilt every token — should record & replay
  • Scheduler assumes discrete VRAM — wasteful copies on UMA
  • Per-op Vulkan dispatch — 200+ descriptor updates/token
  • Full barriers between every op — unnecessary on UMA
  • No CL_Image weight storage — missing Adreno texture cache
  • No GPU+NPU parallel execution — single backend per split
  • No stage-aware kernels — same kernel for prefill and decode
  • No weight rearrangement — row-major from GGUF, not tiled
  • Thread pool busy-waits 50% (battery drain on mobile)
  • GGML_DEFAULT_GRAPH_SIZE=2048 (needs ~500 for mobile decode)
  • 4-copy pipeline parallelism = 2GB waste on mobile
Bottom line: Keep the GGUF loader, tokenizer, sampler, and CPU dot product kernels. Rewrite everything between "graph built" and "result returned": the scheduler, GPU dispatch, memory management, and command recording. This is what pages 4-6 will show you how to do.
