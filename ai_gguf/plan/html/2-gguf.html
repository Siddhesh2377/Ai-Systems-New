01 SOURCE FORMATS

Where Models Start

Models are trained in PyTorch/JAX and published in two main formats. SafeTensors (.safetensors) is the modern standard — zero-copy mmap, no pickle exploits. PyTorch (.bin) uses Python pickle — slower, security risks. Both store the same thing: named tensors with shapes and dtypes.
FormatExtensionSerializationmmapSecurityUsed By
SafeTensors.safetensorsJSON header + raw dataYesSafeHuggingFace (default)
PyTorch.binPython pickle + zipNoRCE riskLegacy models
GGUF.ggufCustom binary + mmapYesSafellama.cpp / your engine
ONNX.onnxProtobuf + compute graphPartialSafeONNX Runtime
Key insight for your engine: GGUF stores no compute graph. It's pure weights + metadata. Your engine must reconstruct the compute graph from the architecture metadata (n_layer, n_head, etc.). This means you can build ANY compute graph — you're not locked into llama.cpp's graph construction.

02 QUANTIZATION

Shrinking Weights Without Killing Quality

A 1.5B FP16 model = 3 GB. Quantized to Q4_K_M = ~900 MB. Quantization maps continuous float values to discrete integer levels within fixed-size blocks (typically 32 or 256 values). Each block stores a scale factor (FP16) that maps integers back to approximate floats during compute.
Block Quantization — Q4_0 Example (32 values per block)
// Original FP16 values (32 floats): [0.182, -0.091, 0.347, -0.523, 0.044, ... ] // 32 × 2 bytes = 64 bytes // Step 1: Find max absolute value in block max_abs = 0.523 // Step 2: Compute scale (delta) d = max_abs / 7 // 7 = max value for 4-bit signed (-8..7) d = 0.0747 // stored as FP16 (2 bytes) // Step 3: Quantize each value to 4-bit integer q[0] = round(0.182 / 0.0747) + 8 = 10 // 0..15 range q[1] = round(-0.091 / 0.0747) + 8 = 7 q[2] = round(0.347 / 0.0747) + 8 = 13 // Step 4: Pack two 4-bit values per byte byte[0] = q[0] | (q[1] << 4) // = 0x7A // Result: 2 bytes (scale) + 16 bytes (32 × 4-bit) = 18 bytes // Compression: 64 → 18 bytes = 3.56× smaller // Dequantize at runtime: value = (nibble - 8) × d // integer math + 1 multiply

Actual C structs from your llama.cpp (ggml-common.h):
// Q4_0: simplest — 32 values, 18 bytes total typedef struct { ggml_half d; // scale factor (FP16, 2 bytes) uint8_t qs[16]; // 4-bit quants, 2 per byte (16 bytes) } block_q4_0; // total: 18 bytes for 32 values // dequant: val = (nibble - 8) × d // Q8_0: used for activations and KV cache typedef struct { ggml_half d; // scale (FP16, 2 bytes) int8_t qs[32]; // 8-bit signed quants (32 bytes) } block_q8_0; // total: 34 bytes for 32 values // dequant: val = qs × d // Q4_K: super-blocks of 256 for better quality typedef struct { ggml_half d; // super-block scale (2 bytes) ggml_half dmin; // super-block minimum (2 bytes) uint8_t scales[12]; // sub-block scales, 6-bit packed (12 bytes) uint8_t qs[128]; // 4-bit quants (128 bytes) } block_q4_K; // total: 144 bytes for 256 values // 8 sub-blocks of 32, each with own scale // dequant: val = sub_scale × d × qs - dmin × min_scale
K-Quants (Q4_K, Q5_K, Q6_K) use a two-level quantization scheme. A super-block of 256 values contains 8 sub-blocks of 32. Each sub-block has its own 6-bit scale factor, and the super-block has a global FP16 scale. This means:
// K-quant dequantization (Q4_K_M) for super_block in weight_tensor: d = super_block.d // global FP16 scale dmin = super_block.dmin // global FP16 minimum for sub = 0..8: sc = unpack_6bit(super_block.scales[sub]) // 6-bit → uint8 mn = unpack_6bit(super_block.scales[sub + 8]) // minimum scale for i in 0..32: q = nibble(super_block.qs, sub*32 + i) // 4-bit value value = d * sc * q - dmin * mn // dequantized float
_M suffix (Q4_K_M, Q5_K_M): "Mixed" quantization — uses higher precision (Q5_K or Q6_K) for the first and last layers, Q4_K for middle layers. These layers are most sensitive to quantization error.

03 GGUF FILE SPECIFICATION

Every Byte of the Binary Format

GGUF is a flat binary format. Magic: "GGUF" (0x47475546), version 3, default alignment 32 bytes. No compute graph, no code — just metadata key-value pairs and raw tensor data. Everything is little-endian.
GGUF File Binary Layout
GGUF4 bytes magic
3uint32 ver
291int64 tensors
26int64 kv_count
KV Metadata Section26 key-value pairs: architecture, vocab, hyperparams, tokenizer, chat template...
Tensor Info Section291 entries: name + shape + type + offset for each tensor
Paddingalign to 32
Tensor Data Blob~900 MB of quantized weight data, packed sequentially, 32-byte aligned

05 ARCHITECTURE METADATA

How the Runtime Knows What to Build

GGUF has no compute graph. The runtime reads KV metadata and constructs the graph from scratch. This is why general.architecture is the most important key — it tells the runtime which class of model to instantiate (LLaMA, Qwen, Phi, Gemma, etc.). Each architecture defines a different graph topology.
Architecture → Graph Construction
// In llama.cpp, model loading works like this: // Step 1: Read "general.architecture" from GGUF arch = gguf_get_val_str(ctx, "general.architecture") // "qwen2" // Step 2: Map to architecture enum switch (arch): "llama" → LLM_ARCH_LLAMA // LLaMA, Mistral, Yi, etc. "qwen2" → LLM_ARCH_QWEN2 // Qwen2 family "phi3" → LLM_ARCH_PHI3 // Microsoft Phi-3 "gemma2" → LLM_ARCH_GEMMA2 // Google Gemma 2 "starcoder2" → LLM_ARCH_STARCODER2 // Step 3: Read hyperparams from GGUF KV n_embd = gguf_get_val_u32(ctx, "qwen2.embedding_length") // 1536 n_layer = gguf_get_val_u32(ctx, "qwen2.block_count") // 28 n_head = gguf_get_val_u32(ctx, "qwen2.attention.head_count") // 12 n_head_kv = gguf_get_val_u32(ctx, "qwen2.attention.head_count_kv") // 2 n_ff = gguf_get_val_u32(ctx, "qwen2.feed_forward_length") // 8960 rope_base = gguf_get_val_f32(ctx, "qwen2.rope.freq_base") // 1000000 // Step 4: Build compute graph (per architecture) // For Qwen2: RMSNorm → Q/K/V proj → RoPE → FlashAttn → O proj → RMSNorm → SwiGLU FFN // For Phi3: LayerNorm → QKV merged → RoPE → FlashAttn → O proj → LayerNorm → FFN // For Gemma2: RMSNorm → Q/K/V → RoPE → SlidingWindow or Full → O → RMSNorm → GeGLU FFN // YOUR ENGINE: You read the same KV metadata, build YOUR optimized graph

06 GGUF: PROS & CONS

Assessment for Your Engine Rewrite

GGUF is the format you're keeping. Here's why that's the right call, and what limitations you'll need to work around.

Strengths

  • Single-file distribution — one .gguf has everything
  • mmap-friendly — zero-copy weight loading, instant startup
  • No compute graph — YOUR engine controls execution entirely
  • Mature quantization — Q4_K_M gives 95%+ quality at 4.8 bits
  • Huge ecosystem — thousands of models on HuggingFace
  • Self-describing — all metadata in the file itself
  • Architecture-agnostic — works for any transformer variant
  • Stable spec — version 3, well-documented, backward compatible
  • Tokenizer included — no separate files needed
  • 32-byte alignment — good for SIMD/GPU memory access

Weaknesses

  • No weight pre-processing — layout is row-major, not optimized for any specific GPU
  • Block quantization assumes uniform importance across all values in a block
  • No CL_Image-ready layout — you'd need to rearrange at load time (like MNN-LLM)
  • Alignment is 32 bytes — not optimal for all GPU cache line sizes (64/128 bytes)
  • Metadata is sequential — no random-access index (must scan all KV pairs)
  • No tensor dependency info — can't parallelize loading
  • Large vocab tensors (embedding/lm_head) are expensive to quantize well
  • No split-device hints — can't mark which tensors should go to GPU vs NPU
For your engine: Keep GGUF as the distribution format. At load time, rearrange weights into your optimal GPU layout (CL_Image tiles, column-major for Adreno, etc.) and cache the rearranged version. First load = slow (rearrange + cache), subsequent loads = fast (mmap cached layout). This is exactly what MNN-LLM and Cactus Compute do.
