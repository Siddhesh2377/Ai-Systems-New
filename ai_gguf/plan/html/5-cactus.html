Cactus Compute

A mobile-first inference engine that abandoned GGUF and GPU compute entirely. CPU + NPU only. Three-tier architecture. Their own file format. 100 tok/s on M4 Pro.

5A — OVERVIEW

What Is Cactus Compute?

YC S2025 startup (San Francisco, 8 people). Founded by Henry Ndubuaku (turned down Nvidia) and Roman Shemet (ex-quant). Source-available, free for students/nonprofits/small business. 500K+ weekly inference tasks in production. Partners: UCLA BruinAI, Yale AI, NUS AI, Imperial, Penn.

Core bet: CPU-first, no GPU compute. 70% of phones lack accessible GPU compute APIs. Instead of Vulkan/OpenCL kernels, they write hand-tuned ARM NEON SIMD kernels per SoC family, with Apple Neural Engine for prefill on iOS.

v0 was llama.cpp-based. v1 rewrote everything from scratch — new file format (.cact), new graph engine (CactusGraph), new kernels. No GGML dependency.

5B — THREE-TIER ARCHITECTURE

Engine → Graph → Kernel

Cactus replaces GGML's monolithic design with three cleanly separated tiers. Each tier has a single responsibility. The graph is lazy-evaluated (built first, executed later via topological sort). Models are per-architecture C++ files — no generic builder.
Three-Tier Stack
FFI Layer cactus_ffi.h — C API, JSON in/out, opaque handles
Tier 1: Engine Model factory, tokenizers (BPE/SentencePiece), KV cache, chat templates, RAG, tool constraints
Tier 2: Graph CactusGraph DAG — lazy evaluation, topological sort, BufferPool, MappedFile (zero-copy mmap)
Tier 3: Kernel ARM NEON SIMD, INT4/INT8/FP16 matmul, online softmax attention, per-SoC tuning
NPU (Apple only) Core ML / ANE bridge — prefill offload on iOS 17+ / macOS 14+
Engine layer owns the user-facing API. Everything enters and exits as JSON. The opaque handle cactus_model_t wraps internal state.
// FFI C API — all functions take opaque handle cactus_model_t model = cactus_init(json_params); // Text completion (JSON in → JSON out) const char* result = cactus_complete(model, R"({ "messages": [ {"role": "user", "content": "Hello"} ], "temperature": 0.7, "max_tokens": 256 })"); // Streaming via callback cactus_stream(model, json_params, callback_fn); // Embeddings const char* emb = cactus_embed(model, "text to embed"); // RAG query (built-in) cactus_index(model, documents_json); const char* answer = cactus_rag_query(model, "question"); // Audio transcription const char* text = cactus_transcribe(model, audio_path);
vs llama.cpp: llama.cpp exposes low-level primitives (llama_batch, llama_decode, manual sampling). Cactus wraps everything into OpenAI-compatible JSON — you never touch tokens, batches, or samplers directly.
Engine components:
- Tokenizers: BPE (engine_bpe.cpp) for Qwen, SentencePiece (engine_sp.cpp) for Gemma/LFM2
- Chat templates: Built-in ChatML, Gemma, custom format support
- KV cache: Sliding window + attention sinking (keep first N "sink" tokens + recent window)
- RAG: Built-in indexing + retrieval via engine_index.cpp
- Tool calling: Grammar constraints + model-specific handlers (gemma_tools.h)
CactusGraph is a DAG with lazy evaluation — closer to PyTorch's approach than GGML's static graph. Nodes are added, then execution uses topological sort.
// Graph API (from graph.h) struct GraphNode { OpType op; // matmul, attention, rope, etc. Tensor* inputs[4]; // Input tensors Tensor* output; // Output tensor OpParams params; // Op-specific params + backend hint }; struct CactusGraph { vector<GraphNode> nodes; BufferPool pool; // Power-of-2 bucket reuse // Build ops (lazy — just records, doesn't execute) Tensor* matmul(Tensor* a, Tensor* b); Tensor* attention(Tensor* q, Tensor* k, Tensor* v); Tensor* rope(Tensor* x, int pos); Tensor* layernorm(Tensor* x, Tensor* w); Tensor* softmax(Tensor* x); Tensor* gelu(Tensor* x); // Execute entire graph (topological sort) void execute(); }; // BufferPool — avoids malloc/free per tensor // Buckets: 256B, 512B, 1KB, 2KB, ... 64MB // Request 3.5KB → rounds up to 4KB bucket → reuse
Weight loading via MappedFile (graph_io.cpp):
// Zero-copy memory mapping class MappedFile { void* data; // mmap'd region size_t size; // File size int fd; // File descriptor // Weight tensor just points into mmap'd region // No copy, no allocation, no deserialization Tensor* get_tensor(const char* name, size_t offset); }; // Scale files loaded alongside weights: // weights/qwen3-0.6b-int4/attn_q.bin → weight data // weights/qwen3-0.6b-int4/attn_q.scale → FP16 scales
Hand-written ARM NEON kernels, not generic backends. Each kernel file targets specific operations with SoC-aware optimizations.

On-the-fly dequantization: Weights are never fully dequantized to FP32 in memory. Each matmul kernel dequantizes one group at a time inside the inner loop, processes it, and moves to the next. This keeps memory footprint at the quantized size.
Apple Neural Engine only — no Qualcomm Hexagon, no Android NPU.
// npu_ane.mm — Objective-C++ bridge to Core ML // Only available on iOS 17+ / macOS 14+ // What gets offloaded: // - Prefill (batch matmuls) → ANE // - Decode (single token) → stays on CPU (NEON) // Why only prefill? // ANE has high launch latency (~2-5ms per dispatch) // For decode (1 token), CPU NEON is faster // For prefill (256 tokens), ANE throughput wins // Dynamic dispatch check: if (params.backend == ComputeBackend::NPU) { ane_dispatch(op, inputs, output); } else { kernel_dispatch(op, inputs, output); // CPU NEON } // Default backend is always CPU // NPU is opt-in per operation via OpParams
No Android NPU support. This is a significant gap — your ai_gguf SDK already has Hexagon NPU scaffolding (nativeSetHexagonConfig), which Cactus lacks entirely. No Vulkan, no OpenCL, no GPU compute of any kind.

5C — .CACT FILE FORMAT

Proprietary Model Format

Cactus v1 abandoned GGUF entirely. Their .cact format is distributed as zip archives on HuggingFace. Simpler than GGUF — no metadata KV store, no tensor info section. Just raw weight binaries + separate scale files + a config.json.
.cact Distribution Format (HuggingFace)
# Example: Cactus-Compute/Qwen3-0.6B on HuggingFace weights/ qwen3-0.6b-int4.zip # 376 MB (INT4 quantized) qwen3-0.6b-int8.zip # 602 MB (INT8 quantized) config.json # 163 bytes — model metadata # Inside the zip: qwen3-0.6b-int4/ ├── embed_tokens.bin # Embedding weights ├── embed_tokens.scale # FP16 per-group scales ├── layers.0.attn_q.bin # Q projection weights ├── layers.0.attn_q.scale # Corresponding scales ├── layers.0.attn_k.bin ├── layers.0.attn_k.scale ├── layers.0.attn_v.bin ├── layers.0.attn_v.scale ├── layers.0.attn_o.bin ├── layers.0.ffn_gate.bin ├── layers.0.ffn_up.bin ├── layers.0.ffn_down.bin ├── layers.0.attn_norm.bin # RMSNorm (FP16, no quant) ├── layers.0.ffn_norm.bin │ ... (repeat for all layers) ├── output_norm.bin └── output.bin # LM head weights
Two quantization levels only — INT4 and INT8. Much simpler than GGUF's 20+ quant types.
// INT4: 16 values per group struct GroupINT4 { uint8_t data[8]; // 16 × 4-bit = 8 bytes float16 scale; // 1 FP16 scale per group }; // Bits per weight: 4 + (16/16) = 4.125 bpw // (vs GGUF Q4_0: 4.5 bpw with per-block FP16 scale) // INT8: 32 values per group struct GroupINT8 { int8_t data[32]; // 32 × 8-bit = 32 bytes float16 scale; // 1 FP16 scale per group }; // Bits per weight: 8 + (16/32) = 8.5 bpw // (vs GGUF Q8_0: 8.5 bpw — identical) // Dequantization (inside kernel inner loop): // value = (int_value) × scale // No zero-point — symmetric quantization only
KV cache quantization:
// KV cache is stored in INT8 with 32-element groups // ~50% memory savings vs FP16 // During attention computation: // 1. Q is FP16 (current token) // 2. K, V are INT8 (cached past tokens) // 3. Dequant K → FP16 on-the-fly for Q×K^T // 4. Softmax in FP32 for numerical stability // 5. Dequant V → FP16 on-the-fly for attn×V // 6. New K, V quantized to INT8 before caching
Convert from HuggingFace to .cact:
# CLI conversion cactus convert <hf-model-name> <output-dir> --precision INT8 # Or via Python script python3 tools/convert_hf.py --precision INT8 # With LoRA fusion cactus convert <model> <dir> --lora <adapter-path> # Steps: # 1. Load HF safetensors/pytorch_bin # 2. Optionally merge LoRA adapters # 3. Quantize per tensor to INT4 or INT8 # 4. Write weight.bin + weight.scale files # 5. Write config.json with architecture metadata # 6. Package into zip archive

5D — PER-SOC KERNEL OPTIMIZATION

ARM NEON — No GPU, No Abstraction

Instead of GGML's backend abstraction (which adds dispatch overhead), Cactus writes direct ARM NEON intrinsics with SoC-family tuning. No Vulkan. No OpenCL. No Metal shaders. Just CPU SIMD optimized for each chip family.

INT8 grouped matmul — the hot path for decode:
// kernel_matmul.cpp — INT8 grouped GEMV (decode) // For single token: y[M] = W[M×N] × x[N] // W is INT8 with 32-element groups, x is FP16 void gemv_int8_grouped( const int8_t* W, // [M × N] INT8 weights const float16* scales, // [M × N/32] FP16 scales const float16* x, // [N] input (FP16) float16* y, // [M] output int M, int N ) { for (int m = 0; m < M; m++) { float32x4_t acc = vdupq_n_f32(0.0f); for (int n = 0; n < N; n += 32) { // Load 32 INT8 weights int8x16_t w0 = vld1q_s8(&W[m*N + n]); int8x16_t w1 = vld1q_s8(&W[m*N + n + 16]); // Load scale for this group float s = (float)scales[m*(N/32) + n/32]; // Dequant + multiply + accumulate // (with DOTPROD: use SDOT instruction) #ifdef __ARM_FEATURE_DOTPROD // 4× faster: INT8 dot product in one cycle int32x4_t d0 = vdotq_s32(zero, w0_lo, x_lo); // ... (4 dot products cover 32 elements) acc = vmlaq_n_f32(acc, vcvtq_f32_s32(d), s); #else // Fallback: widen to INT16, multiply, acc // ~4× slower than DOTPROD path #endif } y[m] = (float16)vaddvq_f32(acc); } }
Build flags: -O3, C++20, aggressive loop unrolling, auto-vectorization. ARMv8.2-A minimum (NEON + FP16). I8MM (SMMLA instruction) detected at runtime on Android, required at compile-time on Apple platforms.
Online softmax attention with INT8 KV cache:
// kernel_attention.cpp — online softmax // No need to compute all attention scores first // Running max and sum → single pass void attention_online( float16* q, // [d_head] current query int8_t* k_cache, // [seq_len × d_head] INT8 int8_t* v_cache, // [seq_len × d_head] INT8 float16* k_scales, // [seq_len × d_head/32] float16* v_scales ) { float max_score = -INFINITY; float sum_exp = 0.0f; float output[d_head] = {0}; for (int t = 0; t < seq_len; t++) { // 1. Dequant K[t] → FP16, compute Q·K[t] float score = dot_int8_fp16( q, &k_cache[t*d_head], &k_scales[t*(d_head/32)], d_head ); score /= sqrt(d_head); // 2. Online softmax update float old_max = max_score; max_score = fmax(max_score, score); float correction = exp(old_max - max_score); // Rescale running sum and output sum_exp = sum_exp * correction + exp(score - max_score); // 3. Dequant V[t] → FP16, accumulate float w = exp(score - max_score); accumulate_v(output, &v_cache[t*d_head], &v_scales[t*(d_head/32)], w, correction, d_head); } // 4. Normalize for (int i = 0; i < d_head; i++) output[i] /= sum_exp; }
Sliding window + attention sinking:
// KV cache management (engine_cache.cpp) // StreamingLLM-inspired: keep "sink" tokens + recent window // Example: sink_size=4, window_size=512, total_tokens=2000 // KV cache stores: [tok_0..tok_3] + [tok_1488..tok_1999] // = 516 tokens instead of 2000 (74% memory savings) // Why keep first 4 tokens? // Attention sinks: initial tokens accumulate high attention // mass regardless of content. Removing them destabilizes // the softmax distribution. Keeping them is cheap.
BufferPool — power-of-2 bucket memory allocation:
// graph_core.cpp — BufferPool // Problem: malloc/free per tensor per token = thousands of // allocation syscalls per second // Solution: pre-allocated buckets with reuse // Buckets: 256B, 512B, 1KB, 2KB, 4KB, ... 64MB // Request 3KB → round up to 4KB bucket // Return buffer after use → goes back to 4KB bucket // Next 3KB request → reuse from bucket (no malloc) // vs llama.cpp: // GGML uses a single large scratch buffer with bump allocation // Pro: zero fragmentation, very fast // Con: size must be pre-determined, inflexible // // Cactus BufferPool: // Pro: flexible sizing, no pre-determination needed // Con: slight fragmentation from rounding, bucket overhead

5E — INFERENCE DATA FLOW

JSON In → Tokens Out

The complete path from API call to generated text. Every step in order.
Complete Inference Pipeline
1. JSON Input OpenAI-compatible messages array via cactus_complete()
↓
2. Chat Template Wrap in model format: <|im_start|>user\n...\n<|im_end|> (ChatML/Gemma/custom)
↓
3. Tokenize BPE (Qwen) or SentencePiece (Gemma/LFM2) → token IDs
↓
4. Cache Reuse Check If new prompt prefixes previous → skip reprocessing cached tokens
↓
5. Prefill (256-token chunks) Build CactusGraph per chunk → dispatch to kernels → populate KV cache. ANE on Apple.
↓
6. Decode Loop Single-token forward pass → sample (temp/top-p) → stream callback → repeat
↓
7. Stop Detection EOS token or custom stop sequences → break decode loop
↓
8. JSON Response { response, function_calls[], confidence, ttft_ms, prefill_tps, decode_tps, ram_mb }
Why chunk prefill to 256 tokens?
// Problem: Processing 2048 tokens at once requires // attention matrix = 2048 × 2048 × sizeof(float) = 16 MB // + all intermediate activations // → memory spike can trigger Android OOM killer // Solution: Chunked prefill const int CHUNK_SIZE = 256; for (int i = 0; i < prompt_tokens; i += CHUNK_SIZE) { int chunk_len = min(CHUNK_SIZE, prompt_tokens - i); // Build graph for this chunk only CactusGraph graph; model->build_prefill_graph(graph, &tokens[i], chunk_len); // Execute (populates KV cache for these positions) graph.execute(); // Memory for this chunk's intermediates freed immediately // (buffers returned to BufferPool) } // Peak memory: 256 × 256 × 4 = 256 KB attention matrix // vs 16 MB for full 2048-token prefill // → 64× memory reduction
Decode loop with INT8 KV cache:
// Decode: one token at a time while (!stopped) { // 1. Build single-token graph CactusGraph graph; model->build_decode_graph(graph, last_token, pos); // 2. Execute (CPU NEON kernels) graph.execute(); // 3. Get logits from output float* logits = graph.get_output()->data; // 4. Sample next token int token = sample(logits, temperature, top_p); // 5. Quantize new K, V to INT8 and append to cache cache.append_quantized(new_k, new_v, pos); // 6. Stream callback const char* text = tokenizer.decode(token); callback(text); // 7. Check stop conditions stopped = (token == eos_token) || check_stop_sequences(generated_text); last_token = token; pos++; }

Cactus Pros

  • Clean 3-tier architecture (vs GGML monolith)
  • OpenAI-compatible JSON API (easy integration)
  • Built-in RAG, tool calling, multimodal
  • Chunked prefill prevents OOM on phones
  • INT8 KV cache + sliding window saves memory
  • CPU-first = no GPU warmup latency (50ms TTFT)
  • Official Flutter/React Native/Swift/Kotlin SDKs
  • Simpler codebase (~60 source files vs 200+)

Cactus Cons

  • No GPU compute at all (no Vulkan/OpenCL/Metal shaders)
  • Proprietary format — 22 models vs thousands
  • Only ~11 model architectures supported
  • No Android NPU support (only Apple ANE)
  • CPU-only decode caps throughput at memory bandwidth
  • Proprietary license (not truly open source)
  • Massive Android RAM overhead (1.2GB vs 76MB Apple)
  • No community model ecosystem
For your ai_gguf SDK: Cactus validates that CPU-first + clean architecture can be competitive. But their no-GPU bet limits them on Android where you already have OpenCL + Vulkan. Steal their good ideas: chunked prefill (256 tokens), BufferPool memory management, sliding window KV cache, and the 3-tier Engine/Graph/Kernel separation. Keep GGUF format and GPU compute — that's your advantage.
