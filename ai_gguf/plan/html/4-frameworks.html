4A — HETEROINFER

GPU + NPU Parallel — 51 tok/s (1.8B)

Tsinghua, SOSP 2025. The killer insight: no single processor saturates SoC memory bandwidth. GPU alone gets 40-45 GB/s of 68 GB/s peak. NPU alone: same. But GPU + NPU together: ~60 GB/s (88% of peak). They have separate memory controllers and cache hierarchies — running both doubles effective bandwidth.

Hetero-tensor splitting: each weight matrix is row-partitioned between GPU and NPU.
// For each MUL_MAT op with weight W[M × N]: // Split W into GPU portion (75% of rows) and NPU portion (25%) W_gpu = W[0:0.75*M, :] // rows 0..75% → GPU W_npu = W[0.75*M:M, :] // rows 75%..100% → NPU // Execute in parallel: gpu_result = W_gpu @ x // GPU computes 75% of output npu_result = W_npu @ x // NPU computes 25% of output // Concatenate results output = concat(gpu_result, npu_result) // The 75/25 split is determined by offline profiling: // Profile GPU and NPU throughput per op shape, // solve constrained optimization to minimize total time
Why 75/25 and not 50/50? GPU has higher compute throughput but NPU has comparable memory bandwidth. The split maximizes total bandwidth utilization, not compute balance.
// Standard sync: clFinish() → ~400μs fixed latency // (blocks GPU driver, flushes pipeline) // HeteroInfer's fast sync: // 1. Predict GPU kernel completion time (from profiling) // 2. Sleep sync thread for predicted_time - margin // 3. Wake up on a small/middle CPU core // 4. Poll a flag bit in the output tensor memory // (GPU writes flag=1 when kernel completes) // 5. Once flag=1, immediately notify NPU → start next op // Result: microsecond-level sync instead of 400μs // Uses one small CPU core for polling — negligible power

4B — ML DRIFT

Tensor Virtualization — 37 tok/s (Gemma2-2B)

Google, CVPR 2025. Key idea: decouple logical tensor indices from physical GPU memory layout. A tensor with logical shape [B,H,W,C] can be stored as a 1D buffer, 2D texture, or 3D texture — the shader translates coordinates at access time. Plus stage-aware kernels: different kernel shapes for prefill (GEMM) vs decode (GEMV). 5-11× over llama.cpp on Adreno.
Tensor Virtualization — Coordinate Translation
// Logical tensor: [B, H, W, C] — batch, height, width, channels // Physical storage: depends on device // 1D Buffer (fallback): index = ((s * height + y) * width + x) * batch + b // where s = ⌈C/4⌉ (4-channel RGBA slices) // 2D Texture (Adreno preferred): texcoord = (x * batch + b, y * slice + s) // Exploits hardware texture interpolation unit // 3D Texture: texcoord = (x * batch + b, y, s) // Best for 3D convolutions // The shader code is GENERATED per-device at compile time // Translation functions injected into kernel source
// PREFILL (seq_len >> 1): Use convolution-style tiled GEMM // - High arithmetic intensity, many output elements // - im2col → GEMM with register blocking // - Quantize activations to INT8 for fast matmul // DECODE (seq_len = 1): Use FC-style GEMV // - Memory-bound, one output row // - Integrate input quantization INSIDE the kernel // (avoid separate quantization pass → save memory read) // - Vectorized loads matched to hardware width // Result: 1,370 tok/s prefill, 37 tok/s decode (Gemma2-2B)
The key insight: prefill can afford to quantize activations to INT8 in a separate pass (amortized over many output tokens), but decode MUST fuse quantization into the kernel to avoid reading activations twice.
// Weight tensor rearrangement for GEMM kernels // From HuggingFace: OHWI (output, height, width, input) // To ML Drift: (G, S_O, O₄, HWD, S_I, I₄) // // G = groups, S_O = output slices, O₄ = within-slice index // HWD = spatial dims, S_I = input slices, I₄ = RGBA channel // // This layout ensures: // - Contiguous 128-bit reads per work-item (4 × FP32 = RGBA) // - Coalesced memory access across work-items // - Matched to hardware texture fetch patterns // // Strategic layout selection: 20% speedup in MUL_MAT alone // Quantization: q8 (all int8) or 8/4/4 mixed // 8/4/4 = int8 attention, int4 embedding+FFN

Pros

  • 5-11× over llama.cpp on Adreno — best single-GPU result
  • Device-agnostic: Adreno, Mali, Intel, Apple — all supported
  • Automatic weight layout selection per device
  • Stage-aware kernels maximize both prefill AND decode
  • Custom operator fusion (RoPE + Q/K/V fused)
  • 20% speedup from layout optimization alone

Cons

  • Google internal — not open source
  • Requires offline weight pre-processing per device
  • INT8 quantization only (no Q4_K style)
  • No NPU support — GPU only
  • No command replay optimization

4C — MNN-LLM

CL_Image Texture Cache — 7.1× Decode, 25.3× Prefill

Alibaba. The breakthrough: store quantized weights as CL_RGBA Image2D objects instead of buffers. Adreno has a separate texture engine with its own L1 cache — Image objects bypass the compute L1, effectively doubling available cache bandwidth. Each work-item loads 128 bits (4 × FP32 RGBA channels) in one instruction.

// Weight memory layout: [l/lp, h, lp] // l = input dimension (reduction), h = output dimension, lp = tile size = 32 // // For a weight matrix [1536 × 8960] (FFN gate): // l=1536, h=8960, lp=32 // Rearranged: [1536/32, 8960, 32] = [48, 8960, 32] // // Stored as CL_RGBA Image2D: // Width = h = 8960 // Height = l/lp = 48 (each row = one tile of 32 weights) // Each pixel = RGBA = 4 × FP32 = 128 bits // // Work-item access pattern: // - Each work-item reads one column of h dimension // - Adjacent work-items read adjacent h values // - → Coalesced reads along h dimension // - → 128-bit load per work-item per tile

// Hybrid DRAM/Flash storage for models that don't fit in RAM // LPDDR5X: ~58 GB/s, UFS 4.0: 450 MB/s - 3 GB/s // DRAM is 19-130× faster than Flash // Strategy: // DRAM: Layer weights + lm_head (85% of model) // Flash: Embedding table (15%) + KV cache overflow // For Qwen2-7B (bfloat16): // Embedding in Flash saves ~2.18 GB of DRAM // Added latency: only 1.4‱ (0.014%) of total inference time // KV cache overflow: // When KV cache exceeds DRAM budget, spill to Flash // Prefetch during MLP phase masks Flash latency // Works up to 3072 tokens before Flash becomes bottleneck

Pros

  • 7.1× decode speedup — biggest single-technique win
  • 25.3× prefill speedup on GPU
  • CL_Image exploits hardware most engines ignore
  • Hybrid Flash/DRAM for oversized models
  • Open source (MNN framework)
  • Both CPU and GPU optimized with architecture-specific tiles

Cons

  • CL_Image only works on OpenCL (not Vulkan)
  • Weight rearrangement needed at load time
  • Custom quantization (not GGUF-native Q4_K)
  • MNN framework is large — hard to cherry-pick
  • No NPU support
  • No command replay

4D — XNET-DNN COMMAND TAPE

Record Once, Replay Every Token — 7-35% Faster

Tencent (WeChat). Record the entire decode compute graph as a command tape on the first token. Every subsequent token replays the tape with a single CPU call — no graph rebuild, no descriptor allocation, no pipeline binding. Like CUDA Graphs but for mobile APIs. Adreno supports this natively via cl_qcom_recordable_queues.
Record-Replay vs Rebuild
llama.cpp (rebuild)
Every token:
1. Build ggml_cgraph (~460 nodes)
2. Allocate 200+ descriptor sets
3. Bind 100+ pipelines
4. Record command buffer
5. Submit to GPU
CPU cost: ~4 ms/token
XNet-DNN (replay)
First token: record command tape
Every subsequent token:
1. Update KV cache pointer offset
2. Update position index
3. Replay tape (single API call)

CPU cost: ~0.1 ms/token
// OpenCL recordable queue on Adreno: // cl_qcom_recordable_queues extension // // 1. Create recordable queue queue = clCreateCommandQueueWithProperties(ctx, device, {CL_QUEUE_RECORDABLE_QCOM, CL_TRUE}, &err); // 2. Start recording clBeginRecordingQCOM(queue); // 3. Enqueue all decode ops (done ONCE) for op in decode_graph: clSetKernelArg(op.kernel, ...); clEnqueueNDRangeKernel(queue, op.kernel, ...); // 4. Stop recording → get recording handle recording = clEndRecordingQCOM(queue); // 5. Replay every token (FAST) for token in generation: // Only update: KV cache write offset, position index clUpdateRecordingArgsQCOM(recording, kv_offset_arg, &new_offset); clEnqueueRecordingQCOM(queue, recording); clFinish(queue); // Vulkan equivalent: reuse VkCommandBuffer // (secondary command buffers, or re-submit same primary) // Update via push constants (no descriptor rebind needed)

Pros

  • Eliminates 90%+ of CPU dispatch overhead
  • Works with any compute graph (not model-specific)
  • Adreno has native hardware support
  • Composable with other optimizations
  • 7-35% end-to-end speedup + reduced power

Cons

  • Only works for fixed-shape graphs (decode)
  • Prefill has variable seq_len → can't replay
  • cl_qcom extension = Qualcomm only
  • Not widely used — limited tooling
  • Modest speedup alone — best combined with others

4E — TRANSFORMER-LITE

FP4 + Sub-tensor KV Cache — 30 tok/s (Gemma 2B)

vivo. Two innovations: M0E4 quantization (4-bit floating point with 0 mantissa bits, 4 exponent bits — dequantization needs just 2 bitwise ops) and sub-tensor KV cache (eliminates the memcpy after each decode step by using pointer arithmetic instead of data copy).
M0E4 vs Q4_0 Dequantization Cost
M0E4 (FP4)
4 bits: 0 mantissa, 4 exponent
Dequant: 2 bitwise ops (shift + mask)
Fused into matmul kernel
1.5× lower latency than INT4 on Mali
Matches INT4 speed on Adreno
Q4_0 (INT4)
4 bits: integer + FP16 scale per block
Dequant: nibble extract + subtract bias + multiply scale
3-4 ops per value
Block scale adds memory read
More complex kernel
// Standard KV cache: copy after each token // KV buffer: [max_seq_len × d_head × n_layers] // After generating token N: // memcpy(kv_buffer, new_kv, sizeof(K) + sizeof(V)) // This COPIES the entire cache to make room — O(seq_len)! // Sub-tensor KV cache: pointer arithmetic only // Pre-allocate full buffer: [max_seq_len × d_head × n_layers] // Each new token writes to offset = position × stride // Attention reads: view into buffer[0..position] // NO COPY — just update the "valid length" integer // For kernel: // K_cache = buffer + layer_offset // same pointer every time // K_len = current_position // only this changes // Savings: eliminates O(seq_len) copy per token per layer // At 4K context, 28 layers: saves ~28 × 4K × 512B = 56 MB of copies/token

Pros

  • FP4 dequant is trivial — 2 bitwise ops
  • Zero-copy KV cache — huge for long contexts
  • Dynamic shape support (variable seq_len)
  • 10× prefill, 2-3× decode over MLC-LLM
  • Works on any mobile GPU

Cons

  • M0E4 has lower precision than Q4_K (no sub-block scales)
  • Not open source (vivo internal)
  • FP4 models not widely available
  • No GPU+NPU parallelism
  • No CL_Image optimization

4F — POWERINFER-2

47B Model on a Phone — 11.68 tok/s

SJTU. The only framework running 47B parameter models on 12GB phones. Key: LLMs have activation sparsity — only 20-30% of FFN neurons activate per token. Profile offline which neurons are "hot" (always active) vs "cold" (input-dependent). Hot → NPU (dense, fast). Cold → CPU (sparse, on-demand from flash). Reduced I/O overhead from 76.7% to 13.7%.
