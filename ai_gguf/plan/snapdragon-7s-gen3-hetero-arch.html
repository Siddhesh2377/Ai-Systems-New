Adreno 810 GPU — Dynamic Parallel Compute

The Adreno 810 is a mid-tier GPU sharing the same silicon die. It excels at dynamic-shape operations — attention computation, softmax over variable sequence lengths, matrix ops that change per-token. For LLM work, it handles attention heads, emotion vector injection, and any op the NPU's rigid graph can't do.

Hexagon NPU — The AI Accelerator

The Hexagon NPU is the fastest AI processor on the SoC — 10× faster than the GPU for GEMM operations. It has two functional units: HVX (vector — handles LayerNorm, activations) and HMX (matrix — handles weight multiply). The 7s Gen 3 adds INT4 support, doubling throughput for LLM weights. The catch: it requires static computation graphs compiled ahead of time.

HVX = Hexagon Vector eXtension. Processes 1024-bit wide SIMD operations per cycle. That's 128× INT8 values per instruction. Used for: LayerNorm, RMSNorm, ReLU/GELU/SiLU activations, element-wise adds, scale ops.

HMX = Hexagon Matrix eXtension. This is the GEMM engine — the workhorse for weight × activation multiplications. Every transformer layer's Q/K/V/O projections and FFN up/gate/down weights go through HMX. It's why NPU is 10× faster than GPU for prefill.

INT4 = 4-bit integer quantization. Each weight uses 4 bits instead of 16 (FP16). This means 4× more weights fit in the same memory, and the HMX unit can process 2× as many INT4 multiplications as INT8 per cycle. For a 3B parameter model at INT4: only 1.5GB RAM needed.

Unified Memory Architecture — The Hidden Superpower

All three processors — CPU, GPU, NPU — access the same physical LPDDR5 RAM. There's no data transfer between them. When NPU writes FFN output, GPU can read it immediately via a pointer — zero-copy. This is fundamentally different from a desktop PC where GPU has its own VRAM separated by PCIe.

Memory bandwidth (25.6 GB/s) is the #1 bottleneck for LLM token generation. To decode one token from a 3B INT4 model, you must read ~1.5GB of weights. At 25.6 GB/s, that's ~59ms minimum — bandwidth-limited, not compute-limited. This is why quantization matters so much on mobile.

Zero-copy = no memcpy between processors. On mobile SoCs, all processors see the same physical address space. NPU writes to address 0x1000_0000 → GPU reads from 0x1000_0000. On desktop, GPU writes to VRAM → PCIe DMA transfer → CPU RAM → expensive!
Desktop (PCIe GPU):
GPU writes → VRAM → PCIe DMA → System RAM → CPU → PCIe DMA → VRAM → other GPU
Cost: 10-50ms per large tensor

Mobile SoC (unified):
NPU writes → LPDDR5 → GPU reads (same address) → GPU done
Cost: ~100ns fence + cache invalidate

The scheduler (running on CPU) decides which processor handles each compute graph node. Static nodes with fixed shapes → NPU. Dynamic nodes → GPU. Floating-point branching logic → CPU. The goal: keep all 3 processors busy simultaneously, never let one starve the others.
Scheduling ruleDetail
Fixed shape opCompile to NPU static graph (QNN SDK)
Dynamic shape opRoute to GPU (Vulkan compute)
Scalar / branchingCPU (single thread, high IPC)
Memory-intensiveCPU or GPU with prefetch
Async backgroundCPU efficiency cores (A520)
Synchronization cost on mobile SoC is ~100ns — just an atomic write to a shared fence variable. On desktop GPU: 1-10ms PCIe roundtrip. This 10,000× difference makes mobile heterogeneous compute actually viable where desktop heterogeneous compute often isn't.
NPU finishes FFN output → writes sync_token=1 to shared RAM
GPU polls: while(sync_token != 1) { /* spin ~10 cycles */ }
GPU reads output → starts attention — total sync cost: ~100ns
No OS call. No driver roundtrip. Just an atomic read in unified DRAM.
Each processor has independent power rails and DVFS (Dynamic Voltage Frequency Scaling). NPU can run at low voltage while GPU runs at high frequency, and vice versa. The NPU's dedicated power rail (added in Gen 2) lets it sustain maximum performance without thermal impact on the GPU.

Token Generation Flow — "What are you feeling?" Through the SoC

Here's what happens on Snapdragon 7s Gen 3 when your emotion LLM generates one token. Each step is assigned to the optimal processor. Total target: ~35-50ms/token for a 1.5B INT4 model.

CPU Tokenize input — "What are you feeling?" → [1, 767, 526, 366, 11214] ~0.5ms
NPU Embedding lookup — token IDs → [1, 5, 896] tensor from weight table ~1ms
NPU Prefill Q/K/V projections — HMX GEMM for all 5 input tokens, all 24 layers ~8ms
GPU Prefill attention — [5×5] attention scores + softmax (dynamic shape → GPU) ~3ms
NPU FFN (all layers) — gate/up/down projections via HMX INT4 ~6ms
CPU Emotion probe — layer 20 residual → 8-class emotion vector (async) ~2ms
GPU Emotion injection — α × emotion_vec added to residual at layer 16 ~0.5ms
CPU Output logits → sample — lm_head matmul + temperature + top-p sampling ~2ms
CPU Fast weight update — outer product v_t⊗k_t → W_fast (async thread) ~3ms async

Your custom forward pass in llama-graph.cpp + GGML backends lets you implement exactly this partition. Each ggml_tensor node can be tagged with a backend: BACKEND_NPU, BACKEND_GPU, BACKEND_CPU. The GGML scheduler routes each compute node to the right hardware automatically.
// Tag FFN matmuls for NPU
ggml_backend_tensor_set(ffn_out, BACKEND_NPU);
// Tag attention for GPU
ggml_backend_tensor_set(attn_scores, BACKEND_GPU);
// Tag emotion probe for CPU
ggml_backend_tensor_set(emo_probe, BACKEND_CPU);
// GGML runs each on the right chip
ggml_backend_graph_compute(sched, graph);
